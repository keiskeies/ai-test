# 09 · 多目标扩展与平台中立抽象

已确认范围：API / Web / Android / **iOS** / **鸿蒙 HarmonyOS NEXT** / **压测** 全部在范围内，界面形态含 标准 DOM、原生+RN、Flutter、H5/WebView(含小程序)、Unity-Cocos-canvas 自绘。

**结论先摆**：这个范围下唯一能让 P0–P4 不返工的做法，是把"平台中立"从口号变成 **P0 就要写死的三个契约**（§1）。契约现在定是 ~3 天成本；P4 之后补是重写 `docs/02` 的 IR 与整个执行层。iOS / 鸿蒙 / 压测的实际实现仍然排在 P5–P7（本文件不假装它们便宜），但它们**必须从 P0 起就被抽象覆盖**，否则第四个平台进来时前面三个会一起烂。

## 1. 三个平台中立契约（P0 定义，不实现）

### 1.1 `TargetAdapter` —— 执行侧唯一扩展点

```ts
TargetAdapter = {
  target: "api"|"web"|"android"|"ios"|"harmony"|"desktop"

  capabilities(): {
    lease: boolean              // 是否需要设备租约（api/web=false，移动端=true）
    snapshotKind: "aria"|"hierarchy"|"pixels"|"none"   // ★ 见 §1.2，全平台最关键的一个枚举
    hierarchySource?: "aria"|"uiautomator"|"xcuitest"|"arkui"|"flutter"
    injection: ("w3c-actions"|"scrcpy"|"wda"|"hdc-uitest"|"adb-input"|"cdp")[]
    streaming?: "scrcpy"|"wda-mjpeg"|"hdc-snapshot"|"cdp-screencast"|"none"
    templateMatch: boolean      // 图像模板匹配可用（视觉类界面的可回放化基础，见 docs/10）
    contextSwitch?: string[]    // 如 Appium 的 NATIVE_APP / WEBVIEW_xxx
  }

  lease(req: DeviceRequirement): Promise<Lease>       // 只有 lease=true 的平台需要
  snapshot(scope?: ScopeRef): Promise<Snapshot>       // {kind, data, sha, capturedAt}
  resolve(loc: LocatorSpec, ctx): Promise<ResolvedTarget>   // 定位阶梯在 adapter 内部实现
  perform(op: Operation, t: ResolvedTarget): Promise<Result>
  release(lease: Lease): Promise<void>
}
```

三条约束：
1. **IR 与引擎只认 `TargetAdapter`，不认 ADB/Appium/Playwright。** `packages/engine` 不许 import 任何平台库（`docs/01` §8.2 那条 lint 规则的延伸）。`adapter-http` / `adapter-web` / `adapter-android` 是并列的包，iOS/鸿蒙只是新增两个包 —— 这是"再加一个平台"唯一不烂的方式。
2. **`resolve()` 在 adapter 内实现，但阶梯的*形状*由 IR 的 `LocatorSpec` 约定**（`docs/02` §6）。每个 adapter 提供自己的 `by` 词表，IR schema 用 `by: string` + per-target 枚举校验，而不是把 Android 的 `resource-id` 写成全局枚举 —— 否则 iOS 进来要改 IR schema，鸿蒙进来再改一次。
3. **能力探测决定路由，而不是运行时报错**。`capabilities()` 结果进 MySQL，Agent 生成 IR 时先查能力（比如目标 app 没开 webview debug 就不生成 WebView 步骤），静态闸据此报错。**理由**：本平台已经真实踩过"模型不支持 tool call 导致运行时全瘫"的坑（`docs/03` §1），同样的错误不该在设计层重犯。

### 1.2 `snapshotKind`：四种快照世界观，不是一种

这是被低估的一处。`docs/02`/`docs/06` 假设了"一份 ARIA 快照同时当模型世界观 + 断言对象 + 自愈指纹"，但：

| snapshotKind | 覆盖 | 指纹基础 | 断言能力 | 定位阶梯可用级 |
|---|---|---|---|---|
| `aria` | Web、WebView | ARIA 子树 sha | 强（结构化文本 diff） | 1–8 全可用 |
| `hierarchy` | 原生 Android、iOS、鸿蒙 ArkUI、RN | uiautomator/XCUITest/ArkUI 子树 sha | 强 | 1–7 |
| `pixels` | **Unity/Cocos/canvas/自绘** | **只有图像** → 必须走模板图指纹 | **弱**（视觉模型不可靠，尤其否定断言） | **只有 7–8 + 模板匹配** |
| `none` | 后台任务、纯 API | 无 | 只能 `db`/`http`/`log` | — |

推论，且必须写进设计而不是留给运行时：
- **`assert`/`assertUi`/`wait{uiPredicate}` 的谓词必须按 `snapshotKind` 分别定义**。pixels 世界里没有"元素存在"，只有"模板命中/未命中"和"视觉模型说存在"。IR 校验要在设计期就拦住：对 `pixels` 目标写 `uiPredicate{state:visible}` 是**类型错误**，不是运行时失败。
- **否定断言在 `pixels` 上禁用**（视觉模型倾向过度报告"存在"，`docs/02` §4 已定这条），只能靠"上一帧有、这一帧模板未命中"这种确定性判据。
- Flutter 特殊：它有 hierarchy，但**默认不输出 semantics → 实际退化成 pixels**。由于已确认"被测端能配合改代码"，Flutter 的正解是 **app 侧开 semantics + `ValueKey` → 拿回 `hierarchy` 世界**，比在测试侧堆视觉兜底便宜一个数量级。这必须写进接入文档并对客户强推（`docs/10`）。

### 1.3 `DeviceLease` 平台中立化

设备租约的语义在安卓/iOS/鸿蒙上必须同构，否则每个平台的调度逻辑都要重写一遍：

```
Lease { id, target, deviceRef{udid|udid|udid}, capabilities, acquiredAt, expiresAt,
        renew(), release(), state: "leased"|"manual"|"needs_human"|"unhealthy" }
```
`state: "manual"` 是 `docs/07` §4 的人工介入锁（人在投屏里操作时自动化必须停），iOS/鸿蒙同样需要 —— **现在就定进契约，不要到时三端各发明一套**。同理 `needs_human`（iOS 首次信任弹窗、安卓 unauthorized 弹窗、鸿蒙未授权）—— **每个平台都有只能人点一下的弹窗，这是共享抽象而非平台细节**，这个洞察晚定一次就要在三个平台各踩一遍。

## 2. iOS（P5）

| 维度 | 现状 | 代价评估 |
|---|---|---|
| 自动化协议 | **Appium XCUITest driver**（与安卓共用 Appium 2 基座与 MCP 工具面 → **这是复用率最高的一条路径**） | 低-中 |
| 定位属性 | XCUITest 元素树：`identifier`（= `accessibilityIdentifier`，testid 的对应物）、`name`/`label`/`value`、`enabled`/`visible`、`x/y/width/height`；支持 `predicate` / `class chain` | 低（`LocatorSpec.by` 留扩展位即可） |
| ⚠ **硬门槛** | **WDA 的构建与签名需要 macOS + Xcode + Apple 开发者账号**（免费账号 7 天过期，企业签才能长期跑） | **这是真护城河级成本**：Mac 池 + 描述文件/证书自动轮换 + Xcode 版本矩阵。商用设备农场把这当卖点卖（`docs/01` §5） |
| 投屏 | WDA 内置 **MJPEG server**（默认 9100 口，帧率/质量可配）`[未核实]`；`mobile: viewportScreenshot`/`destinationScreenshot` 取单帧 | 中。**没有 scrcpy 这种低延迟方案**，MJPEG 帧率与延迟都明显差一档 → iOS 投屏体验上限低于安卓，要有心理预期 |
| 弹窗 | 系统权限弹窗走 `mobile: alert` / `autoAcceptAlerts`（与安卓 watcher 抽象可统一） | 低 |
| 定位阶梯复用 | 阶梯 1–6 逻辑平台无关（指纹、锚点、缓存选择器、置信度门都能复用） | 低 |
| 无法复用 | 设备发现（tidevice/pymobiledevice3 类）、安装与签名、越狱不可用导致的日志/文件访问受限、真机需 USB 插 Mac | 中-高 |

**结论**：软件层复用率高（Appium 基座 + 定位阶梯 + IR + 证据全部复用），**成本集中在物理与签名运维**，不是代码。建议 P5 的前置条件是"有 2 台常插电的 Mac + 一个企业开发者账号"，否则先只做模拟器（iOS Simulator 免签名，但**没有真实 GPU/传感器、推送与后台行为差异大**，能覆盖回归不能覆盖兼容）。

## 3. 鸿蒙 HarmonyOS NEXT（P6）

**NEXT 不是 Android**：无 ADB、无 Android 运行时，`adb`/`scrcpy`/uiautomator 全链路失效。工具链：

| 维度 | 对应物 | 备注 |
|---|---|---|
| 设备连接 | **`hdc`**（HarmonyOS Device Connector） | 命令面与 adb 类似但**不兼容**；有 `hdc list targets` / `hdc shell` / `hdc file send` `[未核实]` |
| UI 自动化 | **ArkUI uitest**（`@ohos.arkui.testing` / hypium）+ `hdc shell uitest uiInput click\|swipe\|text` `[未核实]` | 组件树 dump 与 adb 的 `dumpLayout` 类比 `[未核实]` |
| 定位属性 | ArkUI 组件属性（`id`/`key`/`text`/`type`/bounds）`[未核实]` | 需要 app 侧配合设 `id`/`key` —— 与安卓 `resource-id` 同构，**`LocatorSpec` 能复用** |
| 投屏 | `hdc shell snapshot_display` 轮询截图为主 `[未核实]` | **无 scrcpy 等价物** → 延迟高，体验最差的一档 |
| MCP/开源生态 | 远不如 Appium 成熟 `[未核实]` | 可能需要自己包一层 `hdc` MCP server |

**全部标 `[未核实]`**：本机无外网，鸿蒙工具链细节我无法核实，而它变动很快。**P6 启动前必须做一次可行性 spike**（真机 + DevEco + hdc 实测 dump 延迟、注入可靠性、投屏可达帧率），spike 结论再定实现范围。**不要把鸿蒙当成"再来一个 adapter"直接排期**。

架构上的唯一要求：`target: "harmony"` 与 `snapshotKind`/`LocatorSpec.by`/`DeviceLease` 从 P0 起就是开放枚举（`docs/09` §1）。这个成本是零。

## 4. 压测（P7）

**这是范围确认里影响 P0 最深的一项** —— 它不是加功能，是**执行层的第二种物理形态**。

| 维度 | 功能测试（P0–P6） | 压测 |
|---|---|---|
| 用户数 | 1 | 10²–10⁵ |
| 每步开销预算 | ms 级证据落盘可接受 | **必须趋近 0**（否则测的是自己的 IO） |
| 证据 | per-step 全量（截图/快照/HAR/LLM 原文） | **只有聚合**（RPS、p50/95/99、错误率、TPS 曲线）+ 失败样本抽样 |
| 表达式 | JSONPath/JSONata 每次现编也行 | **必须预编译**（每请求做一次 JSONata 编译 → 测出来的是表达式引擎的天花板） |
| LLM | 设计期可用 | **绝对禁止**（运行时任何一次 LLM 调用都会污染数据） |
| 断言 | 逐条值 | **阈值 over 分位数 + 基线对比** |
| 进程模型 | 单进程解释执行足够 | worker 池 + 连接复用 + 关闭日志 |

### 4.1 不要自研压测引擎

k6/JMeter/Locust 在这一块吃得很死（分布式施压、连接复用、指标聚合、TS 侧 k6 生态）。自研一年都不一定追上，而且**不是本平台的差异化**。

**建议：IR 只当"用例定义"，施压交给 k6。**
```
IR (子集) ──▶ 编译器 ──▶ k6 JS 脚本 ──▶ k6 执行 ──▶ 结果回流同一 runs 模型 + 同一看板
```
- 好处：零施压引擎成本；用例定义仍是平台资产（同一份场景既是功能用例又是压测用例，这是竞品没有的连贯性）；k6 的分布式与指标体系白拿。
- 需要新增：一个 **IR → k6 编译器** + **结果适配器** + **IR 压测子集校验**（静态闸新增一组规则）。
- **子集规则（否则会出现"能编译但语义不同"的假压测）**：
  - ✅ `http`/`openapiCall`/`extract`/`set`/`forEach`(限静态表)/`if`/`wait`(仅常量)/`assert`(阈值型)/`call`
  - ❌ `script`(沙箱开销与不确定性) `assertLlm`(禁止) 一切 `web*`/`android*`/`ios*` 步骤 `sleep`（改成受控 think time）`db`(施压侧连接数是污染源)
  - ⚠ **诚实写进文档：浏览器/APP 界面压测在量级上几乎无意义**（一个 context 数百 MB，10 并发就到顶）。界面层的性能诉求应该走"关键路径耗时基线"而不是并发压测。**这条我会拒绝承诺，因为它承诺了必然后悔。**

### 4.2 对 P0 的唯一改动（现在就要做）

把步骤执行抽成接口，并区分两种运行形态：
```ts
StepExecutor = { run(step, ctx): Promise<StepResult> }        // 功能形态：证据落盘
// 压测形态由编译器把 IR 编译成"预编译计划"，绕过解释器（而不是把证据塞进解释器里做 if 开关）
```
**关键**：热路径要能整体绕开解释器（预编译表达式 + 复用 request 对象 + 跳过事件发射），而不是在解释器里加 `if (perfMode)`。这是"压测支持"从 P0 借的唯一一样东西，成本约半天；不借的话 P7 要重写执行层。

### 4.3 压测真正的产品价值在回归门禁，不在施压

施压是商品能力，**性能回归门禁才是测试平台该卖的**：
```
p95 相对基线退化 > 20% → fail（基线 = 上一版本同环境同配置）
错误率 > 0.1% → fail；吞吐低于容量目标 → warn
性能结论必须带环境指纹（机器规格/连接数/数据量），否则不可比
```
这条让压测和 `perfSmoke`（`docs/05` §3）共用一套基线模型 —— P0 就该把 `baseline` 概念建进 runs 表（成本是一张表），P7 直接复用。

## 5. 重排后的分层（原 P0–P4 + P5–P7）

| 阶段 | 内容 | 新增/变动 |
|---|---|---|
| **P0** | API 单端跑通 | ➕ **三个中立契约（§1）定义但不实现**；➕ `StepExecutor` 接口 + `baseline` 表 |
| **P1** | 服务端化 + 存量迁移首里程碑（`docs/11`，因存量已确认） | ➕ CaseDraft schema + 禅道/Jira/Excel 导入 |
| **P2** | Web adapter + 可视化表 + 自愈 | 不变 |
| **P2.5** | **Flutter/WebView context 切换 + pixels 世界的定位与断言**（`docs/10`） | ★ 新增，**排在 Android 之前**：因为 canvas/Flutter 的可回放化是纯软件问题，先解掉再碰硬件运维，风险更可控 |
| **P3** | Agent 模式 + 轨迹蒸馏 | 不变 |
| **P4** | Android（含设备运维治理、device profile、投屏、人工介入闭环） | 不变，但 adapter 已中立化 |
| **P5** | iOS（Appium XCUITest；前置：Mac 池 + 企业签名） | 新增 |
| **P6** | 鸿蒙 NEXT（**先做可行性 spike**） | 新增 |
| **P7** | 压测（IR→k6 编译器 + 结果回流 + 性能回归门禁） | 新增 |

**P2.5 提前是新答案带来的实质改动**：canvas/Unity 被确认在范围内，而它动摇的是"可回放"这个卖点（`docs/10`），属于**产品根基问题**而非兼容问题，不能等 P4 之后当边角处理。
