# 1B 演示手册（业主版 · 25 分钟）

> 目标：亲眼看一遍 1B 新增的那条链——**编排一个场景 → 调试未保存草稿 → 执行看画布实时进度
> → 报告中心看结论 → 失败步骤单独重跑 → Ctrl+K 找到任何资产**。
> 全程离线可演示：被测系统是本仓库自带的假靶场，不需要任何 API Key，也不需要外网。
>
> 与 1A 手册的关系：1A 讲「一个接口怎么用起来」，本手册讲「多个步骤怎么编排成一个可重复的结论」。
> 装环境那套（§0-§4）与 1A 完全通用，跑过 1A 的机器直接从 §5 开始；
> **但 1B 多一个必须起的进程：Celery worker（§4.2b），不起它场景执行会直接报错，这是设计**（§6.2）。

## 0. 前置

- MySQL 8.x 与 Redis 7.x：**用本机启动的实例**（2026-11-19 业主口径修订，**不再要求 Docker、不再默认远端 db.internal.test**）。MySQL = 本机服务 `MySQL84`（127.0.0.1:3306）；Redis = `C:\Program Files\Redis`（`net start Redis` 或前台 `redis-server.exe --port 6379 --requirepass <你的口令> --bind 127.0.0.1`）。**判定只认「6379 在监听 + `redis-cli -a <你的口令> ping` 回 PONG」**——实测过 `net start Redis` 报成功却无人监听。仓库根 `docker-compose.yml` 只用于生产/Linux。详见 `docs/2026-11-19-metersphere-source-and-local-testing.md` §4。
- Python 3.12（`backend/.venv` 已就绪）、Node 22 + pnpm 10（`web/`）。
- 后端命令一律在 `backend/` 目录执行；Windows 用 `backend/.venv/Scripts/python.exe`。
- Redis 是 1B 的硬依赖（1A 只拿它当缓存，1B 拿它当 Celery broker + 执行事件总线）。
  Redis 连不上时执行会明确报错，不会静默改走别的路。

配置在 `backend/.env`（不入库；模板是仓库根目录的 `.env.example`）：

```ini
TP_ENV=dev
TP_DB_URL=mysql+asyncmy://root:<密码>@127.0.0.1:3306/testpilot?charset=utf8mb4
TP_REDIS_URL=redis://:<你的口令>@127.0.0.1:6379/6
TP_SECRET_KEY=<32位随机串>
TP_BOOTSTRAP_ACCOUNT=admin
TP_BOOTSTRAP_PASSWORD=             # 留空=首次启动随机生成并只打印一次；也可自己设一个
```

## 1. 端口：先避开 Windows 的保留段（30 秒，Windows 用户必读）

```powershell
netsh int ipv4 show excludedportrange protocol=tcp
```

- 这条命令列出 Hyper-V/WinNAT 抢占的端口段。**7999-8098 经常整段被占**，
  所以 uvicorn 用 8000 会报 [winerror 10013]（不是权限不够，是端口不属于你）。
  本手册统一用 **8320**；Linux/macOS 用 8000 也行，改了端口要同步设 `TP_BACKEND`（§4.3）。
- e2e 用的是 8321 / 靶场 9999 / 前端 5173，都已避开保留段，不用管。

## 2. 建表（约 1 分钟）

```powershell
cd backend
.venv\Scripts\python.exe scripts\migrate_dev.py     # 幂等，把开发库推到最新 head
```

- **用这个脚本而不是 `-m alembic upgrade head`**：它会打印当前版本与目标版本，
  并且是全仓第六道门禁（「测试全绿」从来不等价于「演示库可用」——pytest 每轮新建临时库，
  开发库落后几版这件事它一次也照不出来；0014/0015 建完时演示库还停在 0013，就是手工查表才发现的）。

## 3. 起靶场（被测系统，约 30 秒）

另开一个终端，在**仓库根目录**执行：

```powershell
backend\.venv\Scripts\python.exe backend\scripts\target_app.py
```

- 靶场 = 迷你商城 API：`POST /login`、`GET /order/{id}`（要 `Bearer tk-demo`）、`GET /healthz`。
- 1B 为「执行核自测」加了三个可控接口（§14 要求执行核有可控 echo/delay/错误源）：
  - `GET /slow?ms=3000` 故意慢 3 秒（上限 10 秒）——演示画布「呼吸」高亮就靠它拉出时间窗；
  - `GET /flaky?key=abc&fail_first=1` 同一个 key 第 1 次回 500、之后回 200——演示失败重跑；
  - `DELETE /flaky?key=abc` 把计数器清零，同一个演示可以反复演。
- 自检：http://127.0.0.1:9999/healthz 返回 `{"status":"ok"}`。

## 4. 起平台（三个进程，约 3 分钟）

```powershell
# 4.1 种子（可反复执行，只补缺不覆盖手工改动）
backend\.venv\Scripts\python.exe backend\scripts\seed_demo.py

# 4.2 后端（cwd=backend）
cd backend; .venv\Scripts\python.exe -m uvicorn app.server:app --port 8320

# 4.2b 执行 worker（另开终端，cwd=backend）——1B 必须起，见 §6.2
# 这条命令不带 -Q：worker 的默认队列名 = "tp." + TP_ENV（D10/R118 分道）。演示环境
# TP_ENV=dev ⇒ 领 tp.dev；pytest/e2e/verify_worker 各占 tp.test / tp.e2e / tp.verify{ts}，
# 手工 dev worker 从此物理上领不到测试 lane 的任务，不用再为跑门禁专门停它。
cd backend; .venv\Scripts\python.exe -m celery -A app.worker:celery_app worker --pool=solo -l info

# 4.3 前端（另开终端，cwd=web）：preview 跑构建产物，改过源码要先 pnpm build
cd web; pnpm install; pnpm build; $env:TP_BACKEND="http://127.0.0.1:8320"; npx vite preview --host 127.0.0.1 --port 5173 --strictPort
```

- **`--host 127.0.0.1` 不能省**：vite preview 默认只绑 `localhost`，而 Windows 上 `localhost`
  常常只解析 IPv6——那样 §4 让你开的 `http://127.0.0.1:5173` 会直接连不上（本机实测：
  `127.0.0.1` 拒绝连接、`localhost` 才通）。e2e 的配置里用的也是 `--host 127.0.0.1`。

- 种子在 1A 那些资产之外，多建 **1 个演示场景**：「演示：登录-取token-轮询查单-断言」，
  4 步（登录 → 提取 token → while 轮询查单 → 终局断言）。
  **它在场景列表的根层级，不在「交易链路」模块下**（模块是收纳方式，不藏东西）。
- 前端：http://127.0.0.1:5173 → `admin` / §0 里 `TP_BOOTSTRAP_PASSWORD` 的那个值。
- **登录后先在顶栏左侧的项目下拉里选「演示商城」**（或按 1A §5.1 在工作台选一次）。
  没选项目时场景/报告页是诚实的空态「先在工作台选项目」，不是坏了——
  §5 的每一步都默认这一步已经做过。
- `--pool=solo` 是 Windows 必需（1B 的 Celery 在 Windows 上只能 solo 池）。

## 5. 演示路径（25 分钟，照着点）

> 每节末尾的「你会看到」是判据。对不上就跳 §7 排查。
> 演示账号：`admin` / §0 里 `TP_BOOTSTRAP_PASSWORD` 设的那个值。

### 5.1 从用例生成场景（3 分钟）

1. 左侧「场景编排」→ 右上角「**新建场景**」→ **从用例生成** → 勾选 2 个用例 → 生成。
2. 回列表看这一行，再点「新建场景」→「空白场景」对比。

你会看到：生成的场景里每个用例变成一步，**按勾选顺序从上到下排列**。
注意画布上的连线只画**容器包含关系**（循环/分组/判断把子步骤圈在里面时才有线）——
顶层的纯顺序步骤之间**没有箭头**，顺序看列表模式的序号 `1 / 2 / 3`（同一份图的两种画法）。
**这条路和 Pilot 生成场景是同一条数据通路**——1B 交付的是「人选资产生成骨架」。
两条新建路径（空白 / 从用例生成）都**留在列表页**，要用右侧「打开画布」进编辑器——
不会自动跳画布，别以为点错了。
下拉里第三项「让 Pilot 生成」是真入口（1F 已落地）：点它整页跳到 Pilot 试验台（/bench），
项目自动预选，你在试验台里用自然语言让 Pilot 出场景骨架——它不是说明，也不是坏了的按钮。

### 5.2 画布：加步骤、校验、乐观锁（5 分钟）

1. 进演示场景 → 画布右上角在「画布」模式。右键节点/空白处可以插入、复制、禁用、删除。
2. 故意犯错：种子场景里**没有 break 步骤**，先自己造一个——右键「轮询查单」这个循环步
   → 「插入到后…」→「跳出循环」（或左栏逻辑控件「+ 跳出循环」，点它会把新步骤加在
   当前选中节点之后）。这时问题面板写「没有校验问题」——break 在循环里是合法的。
   再切「列表」模式，把这个「跳出循环」行拖到顶层任意位置（比如「登录获取令牌」后面）。

你会看到：节点上立刻出红色角标 `!`，底部「问题面板」列一行
「`n1` **break 只能出现在 loop / foreach 内部，否则执行时没有任何循环可以跳出**」并带「定位」
（面板显示节点 key + 中文说明，规则码 `break_outside_loop` 是这条问题的内部 code，
不直接印在界面上）；**保存被拒绝**（不是保存后跑挂了才发现，红色提示后脏标记还在，
你的改动不会被偷偷丢掉）。后端也有同一道门：绕开界面直接
`PATCH /api/v1/scenarios` 塞同样的坏图，回 422。
**这一节全程不用保存**，做完直接点「返回」，会弹「有未保存的修改 / 留下继续编辑 /
放弃修改并离开」——选放弃，演示场景就还是原样。
3. 开两个浏览器窗口（或一个隐身）打开同一个场景，两边都改一点东西，后保存的那个：

你会看到：**保存冲突弹窗**，标题写明「场景在你编辑期间被别人改过」，
三个选择齐全——「用我的（覆盖对方）」（红色默认**不是**它，默认不覆盖他人）、
「用服务器」（丢弃我方未保存改动）、「复制我的到剪贴板」（谁也不动，自己留着手工合并）。
1B 只有乐观锁 + 差异弹窗，**没有版本历史可回滚**——场景变更历史表按蓝图 §6.5 属二期，
菜单和弹窗里都没留「查看历史」的假按钮。

### 5.3 列表模式：和画布是同一份数据（2 分钟）

1. 顶栏「画布」旁边的「列表」。树形行：启用勾选 + 序号（`1` / `2.1`）+ 类型图标 + 名称 + 摘要。
2. 拖一行换个顺序、勾掉一步、搜索一个步骤名 → 切回「画布」。

你会看到：画布**立刻**跟着变，不需要保存或刷新——两个模式共用同一份内存图，
所以不存在「列表改了画布没变」这种双实现漂移。拖拽换序、复制→粘贴(N)、展开折叠都在列表里做。

### 5.4 场景级设置（2 分钟）

画布上**不选中任何步骤**时，右面板就是场景级面板：基本信息 / 场景变量表 / 失败策略 /
执行超时 / **公共断言** / 定时绑定 / 引用提示。

1. 场景变量加一行 `uid=1` → 保存 → 刷新页面回来看它还在。
2. 失败策略从「遇错停止」切到「忽略继续」→ 保存 → 重新打开，仍是忽略继续。
3. **公共断言**加一条：类型选「JSON 路径相等」，路径 `$.status`，预期值 `ok` → 保存 → 刷新，行还在。
4. 看一眼「定时绑定」。

你会看到：
- 一条都没配时，那一栏明写「**未启用公共断言——各步骤只按自己的断言判定**」。
  没配 vs 配了但没过，必须一眼分得清，所以空态是一句话而不是一片空白（§13 纪律 1）。
- 公共断言是**场景级质量门**：**对每一个真正发出请求的步骤**逐条求值，任一步不过 →
  那一步判「断言失败」→ 整次运行判断言失败。它跟步骤断言共用同一套行编辑控件与同一份
  求值实现（`app/shared/assertions.py` 的 `evaluate`），也共用同一套判定语义
  （`optional` / 遇错停止一视同仁）——不存在「步骤断言一种语义、公共断言另一种语义」。
- **只作用在发出请求的步骤上**：`set_var` / `sleep` / 循环控制器这些不发请求的节点没有
  响应可判，一步都不判、也不报错（拿「没响应」冒充「断言失败」是假红）。
  数据集步按**每一行**各判一次（行与行不共享响应）。
- 什么时候用它：想约束「**每一次调用**」——例如「全场任何一次响应都不许出现
  `{"code":500}`」「每次都要返回 traceId」。只关心某一步就写在那一步的断言里。
- **报告里看得见来源**：公共断言的求值行合并在**它命中的那一步**的断言表里，
  带一个「场景级」紫标——处置动作不同（改场景 vs 改这一步），所以必须分得清是谁没过。
- 场景级面板的「定时绑定」是**真入口**（1E 已交付）：列出跑本场景的定时任务（名称 + cron + 启停态）、
  [去定时任务页新建/编辑] 真跳转，还有一个改绑选择器——把「已绑着别的场景」的既有定时改绑到本场景
  （要 schedule:task:update；新建永远在定时任务页做，这里不抄第二份表单）。
  同理「执行超时」留空表示走全局默认（30 分钟），不是「没有超时」。
- **一处边界要说在前面**：这一栏的改动（场景变量 / 失败策略 / 超时 / 公共断言）
  **算 dirty、离开会拦你、保存才落库，但不进 Ctrl+Z 的撤销栈**——撤销栈记的是步骤树与
  画布布局。实测：删掉一行场景变量 → 黄点亮起，按 Ctrl+Z 变量行回不来、顶栏「撤销」按钮
  仍是灰的（树没动过，它确实没东西可撤）；这时点「返回」会被拦住，库里那份变量
  一个字没变（不会把没存的东西偷偷存掉，也不会弄丢）。
  演示时别顺手秀一句「Ctrl+Z 撤回来」，那一步撤不动。

> **单步重跑也按当时那份门判**：公共断言的配置随每一步的执行明细自包含落库，
> 所以「重跑这一步」即便场景已被彻底删除，结论仍与原 run 一致（不会因为读不到场景就
> 悄悄把红的跑成绿）。这一点评审时通常没人问，但它是「报告自包含」承诺的一部分。

### 5.5 调试：跑一份没保存过的草稿（3 分钟）

1. 随便改一点东西（**不要保存**）→ 点顶栏「调试」。
2. 底部抽屉升起（高度按窗口 35% 取、钳在 120~60vh，1440×900 窗口下正好 300；边缘可拖），
   里面是步骤树 + 每步响应日志。

你会看到：跑的是**你屏幕上那份草稿**，不是库里那份——「不保存也能试」是调试的基本语义。
抽屉里的步骤逐个出结果，终态徽标变绿「通过」。
抽屉底部有「查看报告」入口（带 run_id）。

**一处例外要讲明，别当已知**：调试的**图、变量、失败策略**按屏幕上的草稿走，
但**公共断言按库里已保存的那份**判——入队快照取的是保存行（`ScenarioDebugIn` 没有这个字段，
前端也不偷传一个会被后端静默忽略的字段假装草稿生效）。
所以刚改完公共断言就点调试，看到的可能是旧判定：**改完先保存再调**。

**一个能看出实现诚度的细节**：这时候去「运行记录」能看到这条 run，触发方式是 `✎ 调试`
（图标与文字之间**有一个空格**，`runs.tsx:25` 渲染的是 `m.icon + " " + m.label`；
没空格的那枚是**接口列表**里的徽标，`api.tsx:37`，两个地方别记混）；
但去「报告中心」看不到它。**「最近结果」也不回写到场景列表**——
调试是过程不是结论，「最近结果」只认真执行（§11.4.15 / Review Focus 11）。

### 5.6 执行：画布呼吸 + 取消（4 分钟，本场压轴）

1. 先把草稿保存掉（「执行」跑的是**库里已保存**的场景；有未保存修改时按钮的悬停提示会先让你保存，
   保存不成功就不跑——不拿草稿冒充「执行过的东西」）。
2. 想看清呼吸，得给场景加一步**能慢 3 秒的 HTTP 步**：
   选中任一步 → 左栏逻辑控件点「**+ HTTP 直连**」→ 右侧 URL 填
   `http://127.0.0.1:9999/slow?ms=3000` → 保存。
   **为什么不能直接把「某一步的 URL」改掉**：场景里的接口步骤是「引用用例」（`api_case`），
   右面板只有用例下拉，URL 长在接口/用例里（要去接口管理改）；只有 `http_direct`
   这种一次性直连步才有 URL 输入框。
   **加的位置有讲究**：插在最后一步之后。插在「提取 token」之前会把 extract 的
   `$.token` 抢去对上慢步的响应，执行会如实报「提取失败：变量 token…路径不存在」——
   extract 判的永远是**上一步**的响应，这是语义不是 bug。
3. 点「执行」。

你会看到：正在跑的那个节点在画布上**呼吸高亮**（1.2s 一次；系统开了「减弱动态效果」的话
自动改成静态描边，不闪）。跑完按结果着色：**通过=绿、断言失败=橙、请求失败=红、跳过=灰**。
橙和红是刻意分开的——「断言没过」和「请求根本没发出去」必须一眼能分。
右上角出统计徽标（实跑口径是「共 N · 过 N · 败 N · 跳 N · 错 N · 取消 N」六个数），并有「查看报告」。

**顺手演一个诚实边界**：这条直连步什么断言都没配，于是靶场回 500 它照样**绿**。
这不是 bug 而是口径（与 1A 的「调试」一致：没断言就没有可判的东西），
但界面上不许把它演成「没问题」——直连步的「断言」页签在空态就明写
「**无断言：这一步只要请求发得出去就算通过——目标系统回 500 也是绿的。至少加一条状态码断言**」，
一句话之内给出出口（1A §5.3 接口定义编辑器那句「调试只发请求不校验，建议至少加一条状态码断言」
是同一个口径，`RequestEditor.tsx:267`；场景步这条是 `PropsPanel.tsx:520`）。

### 5.8 报告详情 + 失败步骤重跑（4 分钟）

1. 制造一个失败：加一步「**+ HTTP 直连**」（同 §5.6 第 2 步）指向
   `http://127.0.0.1:9999/flaky?key=demo&fail_first=1`（第一次必回 500），
   然后在场景级面板给**公共断言**加一条「状态码 = 200」→ 保存 → 执行。
   - **这一步的断言也可以直接写在那一步上**：直连步的右面板有「断言」页签，
     与场景公共断言同一套行编辑控件、同一份求值实现。这里选场景级，是为了顺带演掉
     「报告里看得见是谁没过」（紫标「场景级」）与「重跑按**当时那份门**判」两件事。
   - **接口用例步（`api_case`）的「断言」页签是只读说明**，不是编辑页——它的断言跟着用例走
     （在接口管理里改）。想在这条链上直接写断言，就用直连步或场景公共断言。
   - **也别加一个独立的「断言」步骤来当这个失败**：那样红会落在断言步（非请求步）上，
     而单步重跑断言步判的是**当时存下来的响应快照**，不会重新发请求——
     重跑永远还是红的，演示就演不成「重跑变绿」。让失败落在**发出请求的那一步**上才对。
2. 报告中心点这一行进详情。

你会看到三栏：概览卡（通过率环 / 耗时 / 触发 / 环境 / 执行人）→ 左步骤树 →
**中间是场景画布的只读渲染，带结果着色**（和 §5.6 执行时同一套配色，同一份数据）→
右步骤详情：request/response 对照 + 断言结果表（项 / 预期 / 实际 / ✓✗）+ 日志。
点中间画布上的节点，右栏联动到那一步。
3. 选中那个失败步骤 → 点顶部「失败步骤重跑」（按钮只在你选中失败/错误步骤时可点，
   跑的就是**你选中的那一步**：从它落库的快照重建上下文）。

你会看到：**只重跑那一步**（新报告里只有那一个步骤行），生成一条**新报告**（自动跳过去），
顶部挂着紫色「**单步重跑 n1**」标记，并写明「这是步骤重跑生成的报告，来源：原报告」；
**原报告一个字没变**（仍是断言失败、结论原样）。
靶场的 flaky 只败第一次，所以重跑这次是绿的——「同一份快照、只跑一步、上游变量还在」
这三件事在这一分钟里一起演完了（上游 extract 出来的变量在重跑时仍可用，不重放上游）。
因为这条失败是**场景公共断言**判出来的，重跑还顺带演掉一件事：
**重跑按当时那份门判**——报告里失败那步的断言行带着「场景级」紫标，重跑的新报告同样按它判。

**资产删了报告还在**：把一个场景和它的用例走「回收站 → 彻底删除」，
再打开它此前的报告——完整可读，图、结论、步骤明细（含当时的请求/响应快照与断言行）都在。
历史不追删（§14 自包含条款）。
**顺序要先删场景再删用例**：用例还被未回收的场景引用时，回收它会被拒
（`referenced_by_scenario`：「该用例被 1 个未回收场景引用」），这是引用保护不是 bug。

## 6. 三个「为什么长这样」

**6.1 inline 与 celery 的差别（诚实说明）**
执行有两种投递档：`TP_EXEC_MODE=celery`（默认，生产路径）与 `inline`（同进程后台协程，
测试与单机自测用）。**两者跑的是同一份执行引擎**，不是两套实现——所以「测试绿」和
「worker 里跑绿」不是两件事。差别只在**谁起这个协程**：worker 档多一次真 broker 投递、
多一个进程边界。**演示请用 worker 档**（§4.2b），因为你要看的是生产那条路；
pytest 与 e2e 走 inline 是因为不想为了跑单测养一个常驻进程。

**6.2 为什么 broker 连不上就直接报错（以及 worker 没起时其实不报）**
`broker 连不上`（Redis 没起 / 地址错）时执行场景会得到 503 `executor_unavailable`，
明确告诉你执行端没起来，且**不会留下投不出去的孤儿 run**。
**这是刻意的**：静默降级到 inline 会让「生产上跑的是 worker」这句话变成信仰——
演示当场报 503 比线上悄悄换了条路便宜得多（§13 纪律 1）。
**要说清的边界（1C 写手册时实测更正）**：接口探的是 broker 通不通，探不出「有没有
worker 在听队列」。Redis 起着、worker 没起时接口照样回 `200 queued`，那条 run 停在
「排队中」直到 worker 起来。所以「看到 503 去起 §4.2b 的进程」
只对 Redis 侧成立；queued 不动才是「worker 没起」的症状。
**queued 卡住时不要指望点「取消」清掉它**（1C 收尾实测更正，R127）：取消那颗按钮只在
**场景编辑器里、且本地这一轮正跑着**的时候出现（§5.6 那个），报告中心与运行记录页都没有；
后端 `POST /runs/{id}/cancel` 也只是**插一面旗**（`cancel_requested` + 事件总线），
落终态的是执行侧在步骤边界读到旗子——worker 没起就没有人读旗，实测对它发取消回 `200`
而状态仍是 `queued`。真出路只有把 worker 起来，它接走后自己会停在 `已取消`。

**6.3 为什么「调试」不进报告中心**
报告是结论，调试是过程。混在一起，「通过率」就说不清是跑出来的还是试出来的。
调试记录在「运行记录」里一条不少，报告中心默认过滤、可用「含调试」开关查。

## 7. 常见问题

**Q：点执行报 503 executor_unavailable。**
A：Redis 没起或地址错（503 的文案写「worker 未启动或 broker 不可达」，实际探的是 broker
那一路，见 §6.2）。先确认 Redis 在，再看 §4.2b 的进程。
**若是 `200` 但那条 run 一直停「排队中」**：那才是 worker 没起（或起的不是 `--pool=solo`
而在 Windows 上起不来）——把它起起来。别去点「取消」：那种 run 根本没在执行，
取消只是插旗而没人读旗，界面上也没有撤它的按钮（§6.2 / R127）。

**Q：画布上不呼吸，一下就跑完了。**
A：步骤太快。加一步「+ HTTP 直连」，URL 填 `/slow?ms=3000`（§5.6 第 2 步——
接口用例步骤没有 URL 输入框，改不了 URL）。
另：系统开了「减弱动态效果」时呼吸会改成静态描边，那是无障碍设置生效，不是坏了。

**Q：flaky 第二次还是 500。**
A：同一个 key 的计数器还在。`curl -X DELETE "http://127.0.0.1:9999/flaky?key=demo"` 清零，
或者换一个 key。

**Q：报告中心空的，运行记录里有东西。**
A：那些是调试记录，默认被过滤（§6.3）。开「含调试」。另一种可能是时间筛选（默认近 7 天）。

**Q：改了前端源码页面没变。**
A：preview 吃的是 `dist` 构建产物，改完要 `pnpm build`。开发模式 `pnpm dev`（同样要设 `TP_BACKEND`）。

**Q：uvicorn 报 [winerror 10013] / 端口绑不上。**
A：Windows 保留段，见 §1。换端口要同步设 `TP_BACKEND`，否则页面能开但接口 502。
