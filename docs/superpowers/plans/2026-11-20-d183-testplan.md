## 一、这一刀的边界：做什么、明确不做什么

业主口径是「平台功能除 agent 外按 MeterSphere 复刻」，批次 B 顺序已裁：
**测试计划 + 计划报告（143 端点）→ 用例库/评审 → 缺陷 → Mock**。

MS 的计划有 143 端点、19 张建表（GA 时删 1 张，活着 18 张——**不是业主口径的 20 张**，
这条对账文档 §4 已复核三遍）。**照单全收既不可能也不正确**，因为 MS 的计划有一大半
能力是**绑在它自己的其它子系统上的**，而那些子系统我们没有。所以先划边界：

### 整块不做（我们缺它的地基，硬做就是造假）
1. **功能用例关联那一整条腿**。MS 的「计划 × 功能用例」绑 `functional-case` 子系统
   （列表、脑图、状态自动同步、缺陷数、优先级读取全 join 功能用例表）。我们**没有功能用例库**
   → 这条腿不做，对应 MS 三类关联里的三分之一，以及两个脑图端点里的功能用例那个。
2. **用例等级来自自定义字段体系**的那条 join（功能用例的优先级是模板/自定义字段算出来的）。
   我们没有自定义字段体系。接口/场景侧的等级是原生列，不受影响。
3. **计划组（GROUP）**。MS 的组双重绑定：功能开关绑**商业 license**（无 license 时组服务
   直接返回 null），本体只是同一张表里 type=GROUP 的自关联行。我们不做商业位，
   但**也不在第一版做组**——MS 的归档/统计/执行编排全是「组优先」的递归形状，
   砍组必须同步砍统计递归，否则会出现「组能归档、子计划状态却对不上」的裂缝。
4. **缺陷维度**（报告缺陷明细、用例缺陷数、计划缺陷分页）。绑 `bug*` 与缺陷-用例关联表。
   缺陷管理是批次 B 的**第四**刀，在这一刀里它还不存在。
5. **报告附件与富文本图片**。绑文件库/对象存储的临时目录→资源目录转存管线。我们没有文件库。
6. **报告分享（16 端点）与报告布局组件**（自定义仪表板式排版）。整组后置。
7. **照抄 MS 的执行编排表形**。MS 的四级执行队列实体**只存在于 Redis**，它建的
   `test_plan_execution_queue` 表**零读写**（实测，死表）。我们有 `run_record` + worker +
   Redis 租约这一套，语义可映射，**表形不许照抄**。

### 第一版就做（可独立成立的部分）
计划本体 CRUD（含归档）、计划内「关联 × 三种可执行对象」（接口用例 / 场景 / UI·ADB 用例）、
关联行上的执行环境与执行结论、**计划报告 = 生成时刻的一次性快照**、任务中心（计划侧只读进度）。

## 二、从 MS 学到的三条**结构性**决定（不是抄实现，是抄结论）

1. **计划状态只持久化「归档 / 未归档」两值，「未开始/进行中/已完成」查询时现算。**
   MS 的 DDL 注释写着四态，而实际写入的只有两值，中间态是查询时把「全部关联用例的最近
   一次执行结果」映射后算出来的（全成功→已完成，全未执行→未开始，混合→进行中）。
   → **我们照这个形状**：库里只存 `archived` 一个真相，展示态现算。
   理由不是「MS 这么做」，而是**存一列没人维护的枚举就是给未来的自己埋一个说谎的列**
   （见 §三第 1 条，MS 正是在这里翻车的）。
2. **没有「基线/快照」层，快照只发生在生成报告那一刻。**
   MS 的关联表只存指向用例的外键 + 执行态摘要，**不存用例内容副本、不存版本号**；
   计划建立后用例被改，计划永远用最新用例，改动不追溯。只有**报告**是副本：
   生成时把用例当时的名称/模块/等级/最近结果抄进报告明细表，之后用例行怎么改、
   再执行多少次，**已生成的报告数字与明细都不动**（读取路径没有任何重算）。
   → 我们照此：**关联不冻结版本，报告是一次性聚合副本**。这条也顺带回答「报告能不能
   回溯整个执行序列」——**不能，只能回溯生成时被选中的那一次**。
3. **执行环境挂在关联行上，且执行读的是关联行那一份。**
   MS 建关联时从用例抄一份环境进去，执行时用关联行上的环境，而不是用例上当前的环境。
   → 这条必须保留：它就是「同一条用例挂在两个计划里可以用不同环境跑」的全部实现，
   把环境留在用例上会把这个能力丢掉。我们的 `Environment` 表
   （`environment(id, project_id, name, position, config JSON)`）已存在，`run_record.env_id/env_name`
   也已存在（1B 迁移 0014），接得上。
   → **但「从用例抄」这个来源在我们这儿三种 subject 不一样**（本轮现查 models，不是推测）：
   `scenario.env_id`（`scenario/models.py:37`）与 `ui_case.env_id`（`ui_test/models.py:81`）
   是用例上的真列；`api_case` **没有 env 列**（`api_test/models.py` 全文 grep `env` 零命中，
   环境是**执行时**由请求体带进来的：`api_test/services.py:484` 的 `env_id=payload.env_id`）；
   `adb_case` 也**没有**，而且它的模型 docstring 第 14 行写明「§4.5 没列 env_id」是刻意的。
   → 落法：**关联行的 `env_id` 是「这一条关联用什么环境」的权威值，允许为空**；建关联时
   **能抄就抄**（scenario / ui_case 有值则抄），抄不到留空，执行时空值 = 沿用该 subject
   自己的默认口径（api = 请求体给，adb = 无环境）。**不许**为了「统一」去给
   `api_case` / `adb_case` 补 env 列——那是往别人的契约里塞列，且 `adb_case` 那条是 §4.5
   明确排除的。步 2 的用例要分三种 subject 各断言一次（判据 5「各用各的环境」在三种上分别成立）。

## 三、MS 自己没做完的地方 —— 我们**必须自己补**或**明确不做**的环

这几条是取证里最值钱的部分：它们不是「MS 有什么」，而是「MS 声称有但没有」。
照抄这些形状 = 抄一个说谎的实现。

1. **计划「实际结束时间」永远为空**：MS 有 set/clear 两条 update 语句，但**全仓没有任何
   service 调用 set**（copy 流程只往 null 清）。
   → 我们**不做这一列**，直到能说清「计划的结束」由哪个事件定义。没有写入方的列不建。
2. **接口/场景关联行的「最近结果/最近时间/最近报告 id」三件套没有写入方**：插入时写死
   PENDING/0/null，此后全仓（api-test / system-setting / case-management / dashboard 都 grep +
   读实现体过，两个代理独立互证）**无任何路径写真实结果**。后果是实测语义：纯接口计划的
   现算状态**永远停在未开始**，统计全算 PENDING。而 UI 没满屏假数据，是因为列表/报告的
   实时数字是查询时 join 执行报告表现算的，那三列是**没人维护的设计残留**。
   → **这条直接推翻 §二第 1 条的一半**：如果我们在关联行上存「最近结果」，就会种下同一个洞。
   落法：关联行**不存**执行结论摘要，「最近结果」**每次查询 join `run_record` 现算**
   （`run_record.subject_type/subject_id` 已经是这个用途的通用指针）。
   若日后为性能加缓存列，**必须与写入方同刀落地**，并配「缓存与现算不一致时以现算为准」的用例。
3. **执行生成的报告里，接口/场景明细行的执行结果同样无写入方**（执行生成时显式置 null，
   此后唯一的 update 是停止时把未跑的行标 STOPPED）。即纯按 OSS 代码走完整执行，
   汇总通过率恒为「全未执行」——MS 的单测是**手工补写这些列**才让汇总逻辑测得通的，
   坐实「设计上有写入方、开源仓里没有」。
   → 这是**我们必须自己补的环**：报告明细的结果由谁在什么时刻写，必须在同一个提交里有
   代码、有测试，不许留「以后接」的注释。
4. **`允许重复关联`开关在单批内不生效**（同一次批量调用内部仍按用例 id 去重，
   跨两次调用才能重复）——开关语义与实现不一致，半实现。
   → 我们如果做这个开关，**语义要在用例里写死**：一次批量关联请求内是否去重，
   两种选择都行，但不许「开关说允许、实现偷偷去重」。
5. **报告生成整体包在 try-catch 里吞异常只打日志、失败不抛**——执行链路里报告生成失败
   会**静默**。→ 我们的报告生成失败必须**大声失败**（执行可以成功，但「报告没生成出来」
   必须是一个可见的状态，不是一行日志）。
6. 死表两张（allocation、execution_queue）、幽灵字段一个（列已删、DTO 还收、收了丢弃）、
   状态枚举几乎全死（仅通知 i18n 引用）。→ 建表前先问「谁写这一列、谁读它」，两个都没有就不建。

## 四、我们的形状（表名/类名/目录一律自拟，不照抄 MS；走 §5 评审）

已核实的现成地基（不是推测）：
- `run_record`（`app/modules/execution/models.py:16`）**已经是主体无关的**：
  `subject_type`（注释列 api_definition/api_case/scenario/ui_case，实测代码里另有 `adb_case`）、
  `subject_id`（索引）、`subject_name`（**快照名：对象删除后仍可读**）、`env_id/env_name`、
  `trigger`（debug/manual/schedule/agent/webhook）、`status`（passed/failed/error）、
  `stats` JSON、`started_at/finished_at`。**计划报告的数据源就是它，不需要新的执行历史表。**
- ⚠ **但 `status` 那一行的注释是错的**（本轮现查，影响步 3 的现算与判据 3 的通过率）。
  `execution/models.py:25` 写的是 `# passed/failed/error`，而**实际取值有五个、含两个非终态**：
  `new_run`（`execution/services.py:206`）造出来的行出生即 `status="queued"`，
  worker 领取后置 `running`（`scenario/orchestration.py:242`、`ui_test/debug_services.py:315/354`、
  `adb_test/debug_services.py:339/491`），终态才是 `passed`/`failed`/`error`
  （僵尸 run 由租约探活回写成 `error`，`services.py:103`）。
  → **两条硬约束**：① 现算状态判「已执行」只认三个终态，`queued`/`running` 必须归「未执行/执行中」，
    照那句注释写 `status == 'passed'` 之外的都算失败，会把排队中的 run 判成失败；
  ② 判据 3 的通过率分母是**用例总数**、分子是成功数，非终态 run 天然拉低通过率（与 MS 同口径），
    但这必须是**我们算出来的**，不是被那句错注释带出来的巧合。
  步 3 的用例要各造一条 `queued` 与 `running` 的行，断言它们既不算通过也不算失败。
  （`cancelled` / `skip` 是**步骤明细**层的状态，不在 `run_record.status` 上，别混进映射。）
- 权限点命名口径：`域:资源:动作`（实测 `env:config:*`、`schedule:task:*`）→ 计划用
  `testplan:*`，报告用 `testplan:report:*`。
  **本轮实测：权限点没有静态登记表**（`core/permissions.py` 纯 glob 匹配，
  `iam/roles.py:8-16` 四枚内置角色只有模式串：SYSTEM_ADMIN `*` / PROJECT_ADMIN
  `*,-system:*` / MEMBER `*,-*:delete,-*:manage,-system:*,-agent:full:*` / READONLY `*:read`；
  全仓 grep 无 `PERM_CATALOG` 类结构，迁移里也只有角色表没有权限点表）。
  → 新域 `testplan:*` **不需要在任何中心注册**：READONLY 天然只能碰 `:read`，
  MEMBER 天然被 `-*:delete` / `-*:manage` 两条后缀 deny 挡住删与归档。
  由此定死一条：**归档走 `:manage` 而不是 `:update`** —— 归档是单向门（§六 4 无反归档），
  而仓里已有同理由的先例：`adb_test/device_services.py:193-194` 就是为了让
  MEMBER 拿不到强制释放才把门禁位从 `:update` 换成 `:manage` 的。

- 迁移编号现进至 **0023**（`migrations/versions/0023_saved_view.py`）→ 本刀从 **0024** 起。
- `ownModuleIds` / 模块树、`ListPager` 页码、`paginate_page` 都是现成的，不重造。
  `visible_clause` **本刀不用**（理由见下「计划是项目级共享资源」那条，别被这行误导）。

第一版表（**名字已避开 MS**：取证文档 §4 列的 MS 活表里就有 `test_plan` / `test_plan_report`，
我们的表名/类名/目录一律不许照抄 MS——这条边界写在取证文档开头。改走本仓自己的命名族
`run_record` → **`plan_record`**，其余同理，见下。域前缀 `testplan:` 是**权限点字符串**，
不是表名，不受这条约束）：

| 表 | 作用 | 关键取舍 |
| --- | --- | --- |
| `plan_record` | 计划本体 | 只存 `archived`，**不存**状态枚举、**不存**实际结束时间（§三 1/2） |
| `plan_case_link` | 关联行（一张表装三种 subject_type，不学 MS 一类一张） | 存 `env_id`（从用例抄）、不存执行结论摘要（§三 2） |
| `plan_report` | 报告头 | 生成时抄**通过阈值**进报告，此后独立演化（MS 同口径） |
| `plan_report_item` | 报告明细（一次快照的副本） | 结果写入方必须与建表同刀（§三 3） |

**为什么一张 `plan_case_link` 而不是三类各一张**：MS 拆三张是因为三类用例的关联表要 join
各自的用例表；我们的三种 subject 都通过 `subject_type/subject_id` 这对通用指针接
`run_record`（已验证的形状），拆三张只会把「同一概念三份代码」的漂移风险引进来
（本仓这类教训已记过多次：两节各写各的 helper 是**在被守行为不同时**才对，这里行为相同）。

**计划是项目级共享资源，不做行级私有**（本轮定，起因是我在给步 1 派活时写反了这条）：
`plan_record` **不建** `project_public` / `owner_id`，也不用 `shared/visibility.py`。
- 取证文档里 grep 负责 / owner / 可见 / 公开 / 项目级 **全零命中** —— MS 的计划没有行级私有语义。
- 更硬的理由是判据 1：我们这一刀的接口面上**没有任何表单能把 `project_public` 置 false**，
  那建了就是「有 schema 没写入方」的活标本，而本刀存在的意义正是不重犯这个错（§三 1/2/3）。
  列恒为 true = 谓词恒真 = 白建的索引 + 一句会骗人的 WHERE。
- 也别把没这两列的表喂给 `visibility.py`：它读 `getattr(row, "project_public", True)`，
  结果「每行都公开」且不报错（0018 记过账，`schedule/models.py:10-13` 就是为它写的）。
- 落法照仓内最近先例 `schedule_task`：只按 `project_id` 显式过滤，跨项目 = 404 与不存在同码同文案。
  步 1 要有一条**正向**用例断言「同项目成员互相看得到彼此的计划」——它守的是「我们没有行级私有」
  这个决定本身，将来谁顺手接上 `visible_clause` 会红在那里。

**删除语义 = 物理删（照 MS，无回收站）**。MS 的计划删除是物理删 + 级联删关联/执行历史/报告。
我们跟这个语义，但**级联必须与关联表同刀落地**：步 1 还没有关联表，物理删是安全的，
代价是**步 2 建 `plan_case_link` 时必须回头补级联**，否则会出现「计划没了、关联行还在」的孤儿行。
这条债记在本节，步 2 的用例要能证明级联真的发生。

## 六、判据（每步都要过，不接受「看起来对」）

1. **没有任何一列是「有 schema 没写入方」**。每张表每个新列都要能答「谁写、谁读」，
   并在单测里由那条写入路径自己证明它写进去过（§三 1/2/3 三条 MS 教训的合计）。
2. **报告是快照**：生成之后再改用例、再执行 N 次，已生成报告的数字与明细**逐字节不动**
   （断言是「前后两次读报告，整个 payload 相等」，不是「大致没变」）。
3. **通过率口径写死**：MS 是 `成功数 ÷ 用例总数`（**未执行拉低通过率**），
   执行率 = `(总数 − 未执行) ÷ 总数`。我们采同口径并**在用例里钉住**「有未执行时通过率
   必须被拉低」这一条——这条是业务口径，不是实现细节，不许靠读代码默认。
   **「未执行」的定义随本节那条 status 实测一并写死（这半条是我裁的，不是 MS 说的——
   MS 只给了「未执行拉低通过率」，没规定「跑一半」算哪边）**：
   一条关联算「已执行」= 它存在至少一条**终态**（passed/failed/error）run；
   `queued` / `running` 不算已执行（执行率里算未执行、通过率里同样拉低分母），
   但界面上要能显示成「执行中」而不是「没跑过」。
   两个口径的分母都是**用例总数**，不是已执行数。
   理由：执行率要回答的是「还差多少没跑完」。**把「跑一半」算进已执行，执行率就会在
   还有一堆用例在机器上跑着的时候先走到 1.0** —— 而 1.0 这个数字用户读作「都跑完了」。
   开始 ≠ 跑完，这个数一旦混淆就再也回不来了（run 不会从 running 退回 queued），
   所以宁可让它偏保守：跑完才 +1。
4. **归档是终态**：归档后禁止执行、批量操作跳过归档件，且**没有反归档路径**（MS 实测无）。
