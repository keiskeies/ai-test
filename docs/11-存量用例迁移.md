# 11 · 存量手工用例迁移（Excel / 禅道 / Jira）

已确认：**有，成堆 Excel/禅道/Jira 用例**。

**这条答案改变了排期**：迁移不是"以后再说的导入功能"，而是**第一个能产生用户价值的增量里程碑（P1 首位）**。理由很直接 —— 存量用例是团队已有的心智资产和工作量沉淀，"我们能把你们现有的 3000 条用例变成可执行资产"是内部推动落地最强的说法；而"从零写可执行场景"要求团队改变工作方式，推动成本高一个数量级。**用例格式转换器是产品功能，用例迁移是落地策略**，这两件事要分开看。

随之而来：**Qdrant 从 P3 提到 P1**（存量去重与相似检索在 §2 是必需件，不是优化项）。

## 1. 真实输入长什么样（决定了架构，别按理想设计）

我接触过的存量用例，绝大多数不是"结构化数据"，而是**人写的自然语言 + 半结构化表格的混合物**：

| 来源 | 形态 | 典型痛点 |
|---|---|---|
| **Excel** | 列名五花八门（用例编号/所属模块/前置条件/步骤/预期/优先级/用例类型/是否自动化）；**步骤与预期在同一单元格内用 `1.` `2.` 手工编号，或步骤与预期分两列各自编号但行数不对齐** | **步骤-预期错位是第一大坑**：步骤 5 条、预期 3 条，哪条对哪条？合并单元格、跨行粘贴、隐藏行、多 sheet 分模块 |
| **禅道** | `tc_case` 表结构（`product/stage/pri/precondition/caseSteps/expected` 存 HTML/纯文本）；`openedBy`/`lastEditedBy`；套件树（产品→套件→用例） | HTML 里的 `<p>`/`<br>` 编号；**用例与需求(requirement)、BUG 有关联**（这些关联是宝藏，见 §5）；导出权限与 API 版本差异 |
| **Jira（Xray / Zephyr / TestRail）** | Xray：`Test` issue type + `Test Steps` 结构化字段；Zephyr Scale：API 有明确 steps；TestRail：独立系统 + `steps` 富文本 | **同一 Jira 里可能三种插件并存**；自定义字段极多且各团队不同；用例与 epic/story/test execution 关联 |
| **Confluence/飞书文档** | 表格或纯文档描述 | 完全不结构化，纯 LLM 抽取 |

**结论**：迁移必须是**两段式**，而不是一步 LLM 转换：

```
源 → 抽取器（确定性的，按列/字段映射） → CaseDraft（结构化中间态）
     ↓ 抽取不出的部分 → 自然语言正文留在 CaseDraft.raw
     → LLM 充实（把 raw 步骤切成"步骤/操作/数据/预期"四元组，抽取断言，补前置条件）
       → ⚠ 强制 confidence + 逐条人审 + 抽样校准（§4）
     → IR 草案 → 静态闸 → 可执行场景（且**必须保留与源用例的双向链接**）
```

**为什么必须有 CaseDraft**：LLM 一步从 HTML 出 IR，你无法定位"哪一步是猜的"，也无法在 LLM 失败时保留确定性成果。CaseDraft 是"确定性抽取的部分"和"AI 猜的部分"的**分界线**，这条线就是可信度边界 —— 和 `docs/05`/`docs/02` 里反复强调的"AI 的产物必须标明来源与置信度"是同一原则。

## 2. 迁移的三个硬问题

### 2.1 用例粒度不匹配（最反直觉的一个）

手工用例是**验证点粒度**：`步骤: 输入错误密码 → 预期: 提示密码错误`。一条 Excel 用例 = 一个验证点。
自动化场景是**业务流程粒度**：登录页打开 → 输入账号 → 输入错误密码 → 点击登录 → 断言提示 → 断言未跳转。

所以映射关系通常是 **N 条手工用例 → 1 条场景（带 N 个变体）**，或 **1 条手工用例 → 1 条场景 + M 条复用步骤**。

三种映射策略，必须在迁移报告里显式标出用了哪种：

| 策略 | 适用 | 做法 |
|---|---|---|
| **N:1 参数化** | 同一流程不同输入（密码错/账号错/两者都错/超长/空） | 识别"只有数据不同"的用例族 → 合成一条带 `table`/`dataSource` 的场景，**每个变体保留原始用例 id 作为变体标签**（报告里能回溯到禅道原用例） |
| **1:1 + 步骤库** | 独立流程（下单/退款/退款后开票） | 抽取共同前缀（打开 app、登录、进商品页）为 `call` 子场景；**这一步会自然长出步骤库，是迁移的意外高价值副产物** |
| **1:1 独立** | 真正独立的场景 | 直接生成 |

**`data-driven 候选检测` 是迁移的核心算法**：把用例正文归一化（去掉数字、标点、具体值）后算相似度，聚类 → 同簇即参数化候选。**这里 Qdrant 是必需件而非优化**（3000 条用例的两两比较不可行，向量召回 + 簇内精确比较才可行）。这直接推翻了 `docs/04` 里"P0 不引 Qdrant"的前提 —— **Qdrant 提到 P1**，用途是"用例指纹去重与相似检索"，正好也是 `docs/00` §4.7 认定的空白点之一。

### 2.2 断言缺失：存量用例的最大空洞

真实统计里（经验值，`[未核实]`）**超过半数的存量用例没有可自动化的断言**："预期: 正常"、"符合预期"、"页面正确显示"、空着。这些转成场景就是 `docs/00` §6.1 的头号失败模式 —— **永远绿、什么都抓不住的用例**，而且是存量迁移里必然大量遇到的。

对策（组合使用，缺一都会失控）：
1. **`ASSERT_MISSING` 迁移状态**：LLM 无法从"正常"推断出任何可执行断言时，**不要编造断言**，直接标 `needsAssertion` 并进待办队列。
2. **从资源反推断言**（这是平台真正的杠杆，也是纯 LLM 厂商做不到的）：该用例提到"订单列表" → 项目里已有该页面画像 → 生成 ARIA 结构断言；提到"创建订单接口" → 该 operation 已有响应 schema → 生成模糊 matcher（`docs/02` §4）。**断言不是 LLM 从用例文本里想象出来的，而是从你已导入的 API/UI 资源里推导的** —— 这条把"AI 幻觉"变成"资源驱动推导"。
3. **从历史 BUG 补断言**（§5）。
4. 迁移报告必须给出 **"可执行率 / 有断言率 / 需人补断言数"** 三个数，**不要给"迁移成功率"这种合并指标**。合并指标会诱导把"生成了但没断言"算成成功，而这类用例正是平台的信誉负债。

### 2.3 前置条件与环境假设

存量用例写"前置：已有一个已支付订单"，自动化就要真造出来。三条出口（按优先级）：
1. **映射到已有造数子场景**：项目里已把"创建已支付订单"沉淀为 `call` fixture → 直接引用（LLM 按语义在 fixture 库里检索，Qdrant 又一个用途）。
2. **映射到 API 序列**：从 API 资源里推导所需接口组合。
3. **标 `needsFixture`** 并统计 —— 这个数字就是**步骤库建设的路线图**。它是需求清单，不是失败清单，UI 上应该这么呈现。

## 3. 数据模型与双向链接

```
import_sources(id, project_id, kind: excel|zentao|jira_xray|jira_zephyr|testrail|doc,
               config_json, credential_ref, last_sync_at)
case_drafts(id, project_id, source_id, source_case_id, source_url,      -- ★ 反向链接，人审必点
            raw_title, raw_pre, raw_steps_html, raw_steps_text,
            normalized_text, fingerprint, vector_id,
            confidence,                                    -- AI 充实的置信度
            status: pending|drafted|needsAssertion|needsFixture|converted|skipped|duplicate,
            duplicate_of, family_id,                       -- §2.1 用例族
            converted_scenario_id, converted_version_id,
            reviewer, reviewed_at)
case_family_members(family_id, case_draft_id, variant_labels_json)
scenario_links(scenario_id, case_draft_id, kind: covers|partial|regression_of)  -- ★ 覆盖矩阵
```

**双向链接是迁移的第二个价值来源，且比迁移本身更值钱**：
- 正向："这条禅道用例是否已自动化？跑在哪几个场景？最近一次结果？" → **自动化覆盖率**这个指标第一次变成可回答的（覆盖率的分母是真实用例库，不是"我们写了多少脚本"）。
- 反向："这个场景失败时，报告直接显示对应禅道用例号 + 负责人 + 原始步骤" → **红灯能被读懂**，测试负责人能立刻判断严重性。这是推动别人接受平台的关键体验，成本是一张关联表。

## 4. AI 充实环节的可靠性工程

**必须抽样校准，禁止直接采信模型自评置信度**：

```
LLM 充实 → confidence 分桶（如 ≥0.8 / 0.6–0.8 / <0.6）
         → 每桶人工抽 50 条核对正确率
         → 若"模型自评 ≥0.8"桶实际准确率仅 70%，就把阈值提到 0.9
         → 校准表存 DB 并按 prompt 版本记录（prompt 升级后要重新校准，否则阈值失效）
```
其余按 `docs/03` §3 的契约：`generateObject` + zod、失败 repair 2 次、temperature 0、prompt 版本化并钉进 CaseDraft。

三条 UI 硬要求：
1. **并排 diff 视图**：左原始（渲染后的 HTML/表格），右生成结果（步骤/操作/数据/预期四元组 + IR 草案），**AI 推断出的、原始文本里没有的内容要高亮标出**。这是"敢不敢用"的分水岭，比任何 AI 能力本身重要。
2. **批量人审的键盘流**：Y 接受 / N 打回 / E 编辑后接受 / J 下一条。迁移量是千级的，鼠标流会让人放弃审校。
3. **审校结果回流成 few-shot 语料**：人改过的样本进 prompt（或进检索样本库），第二批的接受率应明显上升 —— 这是唯一能让"第二批比第一批便宜"的机制。

## 5. 顺带白拿的金矿：历史 BUG 与需求关联

禅道用例↔需求↔BUG、Jira 用例↔epic/story↔test execution 的关联关系，是团队已经付过成本的结构化知识，而几乎所有 AI 测试工具都只从"文档/代码"生成用例，**没人吃这份数据**。用法：

- **BUG → 回归场景**：某用例关联过 12 个 BUG → 这些 BUG 的复现步骤优先转成回归场景，且这些场景**优先级与门禁等级最高**。`scenario_links.kind = regression_of`。
- **模块 BUG 密度 → 生成优先级**：BUG 密集的模块优先转成场景、优先纳入 CI；BUG 稀疏的先不动。**这直接回答"3000 条用例先迁哪些"这个必然被问的问题** —— 答案不是"全迁"，而是按 BUG 密度排。
- **需求 → 覆盖缺口**：需求已实现但无任何用例关联 → 报"未覆盖需求"，这是测试管理平台层面的高价值报表，且完全不依赖 AI。

## 6. 排期与验收

```
P1 首位（在"服务端化"之前或并行）
├─ M8   CaseDraft schema + Excel 导入器（列名映射配置化，处理合并单元格/步骤-预期错位）
│        验收：真实 Excel 用例 500 条导入，抽取字段完整率报出且错位数可见
├─ M9   禅道 + Jira(Xray/Zephyr) 只读同步器 + 双向链接 + 覆盖矩阵报表
│        验收：任取一个场景，能看到它对应哪条原用例及最近结果；任取一条用例，能答"是否已自动化"
├─ M10  LLM 充实 + 断言推断（从已导入 API/UI 资源推导）+ 置信度校准 + 并排 diff 审校 UI
│        验收：给"可执行率 / 有断言率 / 需人补断言数"三个数，且抽检准确率有报表（不是自评）
└─ M11  Qdrant 用例指纹 + 参数化候选聚类（data-driven family）+ fixture 语义检索
         验收：同一流程的 8 条变体用例自动聚成一族并给出参数化草案，人审接受率 > 70%
```

依赖关系注意：**M10/M11 需要 API/UI 资源已入库**（断言从资源推导、fixture 从库里检索），所以 M8–M11 应排在 P0 的 M5（OpenAPI 导入）之后 —— 这正是它落在 P1 而不是更早的原因。

## 7. 需要用户拍板的问题

| # | 问题 | 为什么影响大 | 我的默认 |
|---|---|---|---|
| M-1 | **具体是哪个系统**：禅道开源版/企业版/自研二开？Jira 装的是 Xray / Zephyr Scale / Sync Tools / TestRail for Jira？ | **决定导入器形态**：开源禅道可直连 DB 全量拉；企业版/二开只能走 API 或人工导出。Xray 和 Zephyr 的 API 完全不同 | 先做**通用 Excel 导入器**（覆盖所有来源），再针对性做 API 同步器 |
| M-2 | 存量**数量与字段现状**：大概多少条？有没有"步骤/预期"分列且对齐的规范用例？ | 规范率高 → 确定性抽取为主，LLM 只补断言（成本低、可信度高）。全是自然语言 → LLM 是主路径，审校成本高一个数量级 | 假设 30% 规范、70% 半结构 |
| M-3 | **谁来做迁移审校**？有几人、能投入多少时间？ | 3000 条按每条 40–90 秒审校 = **30–75 人时**。没人审校 → 只能迁"规范率高"的那部分，其余降级为"参考关联"（只建链接不生成场景）。**这是本项目最容易在落地阶段崩掉的地方**：把一堆没断言的用例塞进 CI，红灯会被当成"迁移失败" | 先迁 BUG 密度最高的模块（§5），控制在 300 条内首批 |
| M-4 | 历史 **BUG 数据是否可访问**、是否与用例关联？ | 有 → §5 整套白拿，且能回答"先迁哪些"。没有 → 优先级只能按模块人工定 | 假设可访问 |
| M-5 | 目标是**全量迁移**还是**规范驱动新写**？ | 我强烈建议后者为主、前者为辅：**存量全量迁移会把平台变成"旧用例的执行器"**，而旧用例的断言质量决定了平台红绿的上限。真正的价值是"存量当知识 + 资源驱动新写" | 首批迁 BUG 密集模块；其余只做链接与覆盖矩阵，不强行生成场景 |
| M-6 | 用例里的**测试数据**是写死的吗（具体手机号/订单号）？ | 写死 → 迁移后必然在别的环境失败，需要"数据占位符化"规则（`docs/05` §5） | 迁移时统一把疑似唯一值/手机号/身份证形态转成生成器 |
