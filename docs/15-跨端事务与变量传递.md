## 1. 三端共享变量空间：已交付的那一半

这是 `docs/00` §4.1 认定的第一空白点，**它真的能跑**，不是纸面设计：

| 能力 | 实现位置 | 状态 |
|---|---|---|
| 步骤出参被后续步骤引用（`$.<stepId>.<path>`） | `interpreter.ts` 里各步骤 case 的 `vars.exportStep(...)`（数一下：`grep -c 'vars.exportStep(' packages/engine/src/interpreter.ts`，**这里不钉数**）+ `vars.ts:resolveRef` | ✅ |
| 并行分支各自一份作用域、跑完并回 | `vars.ts:forkBranch` / `adoptFrom` | ✅（详见 §2） |
| 子场景（`call`）的变量隔离 | `call` 步骤建一个**全新的** `VarSpace`，内容只有 `call.args`（在父作用域里逐个求值）+ 子场景自己的 `inputs.default` | ✅ |
| 设备句柄跨端继承 | 租约槽（本轮从 `stepCtx.lease` 拆成独立的 `LeaseSlot`，见 §3.8），**不是全局状态** | 部分，见 §3.1 |
| 密钥 | `secret:<ref>` 占位，只在发请求那一跳解析成真值；Agent 上下文永远只见占位符 | ✅（`docs/02` §5） |

两条**容易被当成 bug 而其实是刻意设计**的规则，读代码的人会先困惑一次：

1. **子场景读不到父场景的临时变量，一个字都读不到。** 不是"传了父空间但被隔离"，是**压根只传 `call.args`**：
   每个 arg 在**父作用域**里求值完，作为子场景的 `inputs` 建一个全新 `VarSpace`（`interpreter.ts` 的
   `case 'call'`）。所以父变量要往下走，必须在 `call.args` 里显式写一遍。
   **这条是刻意的**（`docs/02` §8 双向同步依赖它 —— 两边各写各的空间会互相踩），
   而它顺带解释了下面第 2 条为什么容易写错：往下的通道是"显式列 args"，往上的通道就不是了。
2. **只有子场景 `outputs[]` 声明过的值回得来。** 而且回的方式是 `vars.set(assignTo, rep.outputs)`，即挂在 `assignTo` 上，**不是**挂在那个 `call` 步骤的 id 下。所以引用写法是 `$.<assignTo>.<字段>`，写成 `$.<call 步骤 id>.outputs.<字段>` 会解析不到。

> 上面第 1 条是**直接读 `case 'call'` 那三行**得到的（`childVars` 的构造参数里只有 `s.args` / `child.inputs` / `env` / `secretResolver`，没有任何父空间的引用），这条我确信。
> 第 2 条**没跑过实测**：`call` 有测试，但没有一条测"父步骤用子输出当 ref"。真要动这条，先补测试再动语义，别照这一格改。

## 2. `parallel` 的合并规则：先声明者赢

`adoptFrom` 里那一句是全部：

```ts
if (this.has(k)) continue; // 外层或先并的分支已有：不覆盖（先声明者赢，顺序固定 → 结果确定）
```

**判据是 `has`（只看帧），不是 `knows`（帧 + inputs + env）**，理由记在原注释里，而它值得抄一遍，因为这是本仓反复出现的那类坑：

> 顺序执行时 `set token = "x"` 而 `token` 只存在于 env/inputs，走的是 `declare` —— 在当前帧新建一个遮蔽它的变量。若这里用 `knows`，env 里有 `token` 就跳过合并，于是**同一步写在 `parallel` 里会被静默丢弃、写在 `parallel` 外却生效** —— 同一份 IR 挪个位置就换行为。

**"并行与顺序同语义"是这条规则的验收标准**，不是附加说明。改这段代码前先问：改完之后，同一条 IR 放进 `parallel` 和放在外面，结果一样吗？

配套的确定性问题（已落地，`interpreter.ts` 的 `parallelHazards`）：分支里出现 `useIdentity` 会报 lint —— 并行分支共享身份状态，结果随调度顺序变化。**共享变量名**是同一个问题的另一面，上面那条"先声明者赢"就是它的确定性兜底。

#### `inheritToChildren`：为什么"父租约传下去"不是补一行透传（本轮实测）

**症状先说**（探针在 `.scratch/probe-child-lease.mts`，跑的是工作区代码；
永久落点 `lease-inheritance.test.ts`「父场景 setup 里的租约**不跨 call 边界**」）：父场景 `setup` 里 `device` 拿到 `L1`，`call` 一个 body 只有 `tap` 的子场景 —— adapter 调用序列是 `lease → release`，**中间的 `tap` 压根没发出去**：

```
父 = seed:pass, d:pass, c1:error      子 = seed:pass, t:error（"执行设备步骤前缺少 device 租约"）
```

而 IR 上 `inheritToChildren` 是 **`default(true)`**，字段注释写着"后续步骤隐式继承租约（`docs/08` §3 未决问题，**先按继承实现并允许显式关闭**）"。所以按字面读，今天的行为**与字段承诺相反**：默认该继承，实际没继承，而且**关不掉**（没人读它）。

**但我没有顺手把租约槽透传下去，三个理由各能单独否决这次"顺手"**：

1. **lint 与运行时会当场对不上。** 探针同时跑了 lint：子场景那条裸 `tap` 已经被 `RESOURCE_LEASE_MISSING`（`level:'error'`）判死 —— 也就是说 **lint 与运行时今天是同一口径**（两边都说"子场景得自己拿租约"）。只改运行时，就变成**静态闸拒掉一个运行时能跑的写法**，而那条报错的理由（"之前没有 device 租约"）与运行事实直接矛盾。这正是 §3.3/§5.1 里那条 `RESOURCE_LEASE_MISSING` 误报的形状，本轮刚把它修掉一次，不该反方向再造一条。
   要改就得**同时**告诉 lint "call 的父侧可能带着租约进来" —— 而 lint 逐场景跑，**父是谁它不知道**。
   （**本轮之后要改口**：`ctx.scenarioGraph` 现在**有生产者了**（`cli` 的 `buildScenarioGraph`，
   沿 resolver 走可达闭包，`atest lint` 与 `run --strict` 都填它），所以"拿不到调用图"这个前提
   已经不成立了。但它只是**必要条件之一**：那张图今天是"谁 call 谁"，
   要支撑这条判据还得带上"父在它自己那一层走到这一步时手里有没有租约"——
   那是一个**与步骤位置相关**的属性，不是场景级的一个开关。见 `docs/14` §5 那一行。）
2. **子场景的 `finally` 会无条件把它还掉。** 解释器收尾是"有租约就 `release`"。父把 `L1` 传下去，子场景结束时那一层就会**把父正在用的那台设备还回池子**，父后面所有设备步骤跑在一台已经被别人领走的机器上 —— 而报告的证据与结论看起来是连贯的一整条。要修就得引入**归属**（继承来的只解引用、不归还，见 `Lease.holder`），那是新增语义，不是透传。
3. ~~**`parallel` 那一支今天压根不共享 `stepCtx`**~~ —— **这条当时写错了，而错法本身值得留**。
   我的推理是"`runStep(c, …, branch, branchWindow)` 这个调用点里没有 `stepCtx` 形参，所以分支不共享它"，
   而 `runStep` 是 `runScenario` 作用域里的**闭包**（`interpreter.ts`），它读的 `stepCtx` 来自**外层作用域**、
   不是形参 —— **"调用点没写"根本推不出"读不到"**。实测（`.scratch/probe-parallel-lease.mts`）：
   租约在 `setup`、`parallel` 两支各一个裸 `tap` ⇒ 调用序 `lease → perform → perform → release`，
   **两支都跑通了，而且只 lease 一次**，也就是说它们**确实共享**外层那台
   （永久落点 `lease-lifecycle.test.ts`「租约在 setup、parallel 两支裸 tap → 两支共享同一台且只 lease 一次」）。
   这个错法的来源见 §3.7 末段（同一段代码里 `runScenarioIn` 收了四个没人读的参数，
   也是"从调用参数表推行为"推出的）。**从调用点推语义之前，先确认那个函数是不是闭包。**
   共享这件事后来被证实是一个**真缺陷**（不是这条推理的附属问题），另起一节讲：见 §3.8。
   共享既然是事实，原来的结论要改口：不是"`call` 与 `parallel` 的继承语义必须不同"，
   而是"**`parallel` 已经在继承（并且继承错了），`call` 压根不继承**" —— 两个方向都和问题陈述不一样。

**所以这一条的正确修法不是透传，是二选一，而且要连带 lint 一起定**：
- **A：语义就是"不跨 `call` 边界"**（今天的行为）。那 `inheritToChildren` 这个名字与 `default(true)` 是**误导** —— 它暗示"默认继承、可以关"。改法是**把字段改掉**（删掉，或改成 `inheritWithinScenario` 之类只描述本层后续步骤的名字），而不是留着让人写 `false` 并以为关掉了；
- **B：真继承**。那要同时做四件事：`slot` 透传进子运行（`LeaseSlot` 这层抽象本轮已经为 `parallel` 建好了，`call` 只差一跳）、**归属**（继承来的不还 —— 这条也已经有实现：`LeaseSlot.owns`，本轮为 `parallel` 加的）、lint 侧知道"call 可能带着租约进来"（要么给 `scenarioGraph` 生产者，要么把这条 error 降成"拿不到调用图时不判"）、`parallel` 分支明确**不继承**并说明理由（本轮已按这条做了：分支各一个槽，理由见 §3.8）。

  **也就是说 B 的四件事里有两件本轮顺手做完了**（都不是为了 B 做的，是为了修 `parallel` 那个漏还）。这既是好消息也是风险：好消息是 B 变便宜了；风险是**"剩下的事看起来也差不多了"**这种错觉 —— 剩下的两件（lint 知道调用图、`inheritToChildren` 这个字段本身怎么处置）一件没做，而那两件才是 B 真正贵的地方。
  > **本轮之后这两件的样子变了，而"没做完"没变**：调用图那一半**生产者有了**（见上面第 1 条那条改口），
  > 但它今天只记"谁 call 谁"，**记不了"父走到那一步时手里有没有租约"** —— 那才是这条判据要的东西。
  > 所以"图有了"离"lint 能判这件事"还差**图的内容**，不差图的**来源**。
  > 这正是本轮该写下来的一句：**补齐一个前提，不等于补齐那个结论**；
  > 而如果只因为"图终于有了"就顺手去接这条判据，接上的会是一张答不出这个问题的图，
  > 而它答不出时的表现与"判过了、没问题"逐字相同（`docs/14` §5 那一整行讲的就是这件事）。

**这一条的价值不在"缺一个功能"，在"字段名 + 默认值 + 注释三样一起描述了一个没人实现的语义"**：写用例的人读 IR 会以为继承是默认行为，于是父子各写一个 `device` 步时以为"会不会占两台"，而实情是**必须**占两台（否则子场景直接 error）。这与 §3.2 `dbRow` 那条"注释承诺绑定、实现不绑"是同一种，而比它更隐蔽一层：**这里连默认值都在替那句假话背书**。

**这一族的共同形状**：契约定得比实现齐 —— `Lease` 有四态、`device` 步有三个可配字段，而执行侧只兑现了**生命周期**（拿、续、还、覆盖前还、异常时也还）。四态与两个开关仍悬着，而**它们悬着的方式是"能写、能过校验、行为不变"**，正是 `docs/08` §3 那一族的形状。


### 3.2 `dbRow` 的 SQL 绑定：文档与实现相反 ✅ 已修（含对本节原判断的两处更正）

IR 的字段注释从前是这个样子的（`waits.ts`）：

```ts
/** 只读 SQL；$var 占位由引擎绑定（禁止字符串拼接） */
sql: z.string().min(1),
```

而三个 `db.query` 调用点里，**只有一个真的绑定**：

| 调用点 | 改前传进去的变量 | |
|---|---|---|
| `interpreter.ts` `case 'db'` | `strMap(s.vars, (v) => resolveValue(v, vars))` | ✅ 绑 |
| `interpreter.ts` dataSource 处 | `{}` | ✗ |
| `wait.ts` `case 'dbRow'` | `{}` | ✗ |

**下面那句是本节原先写错的地方，先更正。** 原文说那个报错"每轮变成『还没满足』，**直到超时**"，读起来像会轮询到超时点。**改前**实测不是（`.scratch/probe-dbrow.mts` 系列；
"两种真相必须分得开"这件事今天的永久落点是 `lang.test.ts`「真·超时与"第 1 轮就中止"必须在报告上分得开」）：

```
db.query 被调用次数： 1        （真·等满超时会是很多次）
waitedMs = 0 / polls = 1
摘要     = 等待超时（2000ms）：数据库出现匹配行（default）
```

一次都没等到 —— 但摘要说等满了 2000ms。**"每轮都失败"与"第一轮就中止"给出逐字节相同的结论**，而这恰恰是更难查的那一半：值班人看到"等满了 2 秒"会去查"2 秒内为什么没落库"（查产品、查异步链路），而真相是那条 SQL 压根没被数据库接受。机制记错一次，就会把修法定成"让错误可见"，而真正要修的是**两种真相不能共用一句话**。

#### 3.2.1 落地的三件事

| | 做了什么 | 为什么是这个形状 |
|---|---|---|
① **绑定接上了** | `wait{dbRow}.vars` 与 `dataSource.source.vars`（都是 `.optional()`），三处 `db.query` 现在共用同一个 `strMap` + 同一个 `resolveValue` | 选"接上"而不是"禁止 SQL 里出现 `$"`：后者要用一条 IR 校验去否定一种直觉写法，而 `db` 步早就有同名同义的 `vars` —— 语义已经定在那儿，**这里不需要新造约定**。`strMap` 从 interpreter 闭包搬到 `resolve.ts`，因为长在闭包里正是 `wait.ts` 用不到它、于是传了 `{}` 的直接成因 |
② **两种真相分开了** | `WaitResult.evalError` + 解释器里"一次都没求成"那一支；缺 adapter 的四种条件升级成 `NoConditionAdapter` 外抛 | `evalError` 单独立字段而不是"看 describe 里有没有『求值报错』"：describe 是给人看的摘要，**给摘要文本编程**等于改一句文案就让调用点静默换边 |
③ **`onTimeout:'continue'` 不再能把它洗成 pass** | 条件跑不起来时三种 onTimeout 全部汇成 `error + env-unavailable` | 见 §3.2.3 |

#### 3.2.2 `sql` 里的 `$` 到底是什么占位 —— 一个刻意没有回答的问题

写静态检查时最容易顺手做的事，是把判据写成"`$oid` 在 `vars` 里没有同名键 => 报"。**这个判据要先规定"`$oid` 指的是 `vars.oid`"**，而：

- MySQL 的具名占位是 `?` 或 `%(oid)s`，**`$` 连标准都不是**；
- Postgres 里 `$$引用$$` 是合法语法；
- 全仓没有任何一处文档、schema、测试规定过 SQL 里的 `$` 是什么。

**`docs/02` §3 那两个例子是这句话的源头，本轮一并改了**（`WHERE id=$id` 与 `WHERE id=$.mk.resp.data.orderId`）—— 它们没"规定"`$`，只是**示范**了一种写法，而示范比规定更容易被照抄。改后的例子把值挪进 `vars`，占位写成 `:id` 并**在例子旁边注明这个写法不是规定**。**今天没有任何一个 db adapter 实现**（`DbExec` 只是 `adapters.ts` 上一个端口，`grep` 全仓没有实现方），所以此刻规定 `:id` 还是 `%(id)s`，等于再造一次"注释承诺了一件没人实现的事" —— 那正是本节要修的那个形状。**等真有 adapter 时再定，且由那个 adapter 的那一轮来定。**

所以那个判据等于**由 lint 发明一种占位语法**，正是本仓那一族"引擎现猜"，只是这次猜的人换了地方。最终判据只剩一条当下为真的话：**`$x` 不是本 IR 规定过的任何占位写法，而引擎不做任何 `$` 替换** —— 只要 SQL 里出现 `$` + 标识符就提醒，不看 `vars` 里有没有对应的键。

**这条判据是被自己的变异集问出来的**，而那段过程比结论值钱，记在 `tooling/mutate/wait-not-wired.json` 的 L5：第一版判据是"`vars` 是空的才报"，跑出来 **survived**，我一开始以为是测试写得不够好，真相是**规则本身漏了最主流的错法** —— `WHERE id = $oid` 配上 `vars:{oid:…}`（作者两边都写了，看着什么都没缺），MySQL 照样拒那条 SQL。**判据太窄的时候测试全绿，只说明测试与规则一样窄。**

#### 3.2.3 `onTimeout` 管的是"等不到"，不是"没法等"

改前实测四种条件缺 adapter 时（`.scratch/probe-dbrow4.mts`）：

| `onTimeout` | 改前 | 现在 |
|---|---|---|
| `fail` | fail + env-unavailable，摘要「等待超时（1000ms）」 | error + env-unavailable，摘要点名缺哪个槽位 |
| `continue` | **pass**，且**整场结论 pass**、退出码 0 | error |
| `error` | error + env-unavailable（**这一档反而是对的**，因为它不看原因） | 同上 |

`continue` 那一档是本仓目前最贵的一个假绿：**一个没有任何 db adapter 的 `wait{dbRow}`，整场报绿，而它一次数据库查询都没发出去过。** 界线不是文字游戏：`onTimeout` 是作者对**产品事实**的容忍（"等不到也继续走"），而"这条条件今天压根跑不起来"是**平台/用例事实** —— 作者写下 continue 时从没被问过"连条件都跑不起来也要继续吗"。让它 pass 等于让后面每一步都建立在一个没验证的前置上。

顺带对齐了归因：等待条件里引用一个不存在的变量，改前报 `env-unavailable`，而**同一个未定义引用**写在 `db` 步的 `vars` 里或 `extract` 的 `from` 里报的都是 `case-stale`（`.scratch/probe-varref.mts`）。`env-unavailable` 不只是难听 —— CI_HINT 教 CI 对 error **重试一次**，而一个不存在的引用不会因为重试而出现；更要紧的是看板按 cause 分组，这一类会被记进"环境问题"，把真正的环境问题稀释掉。修法是 `wait.ts` 把 `VarError` **原样外抛**，让解释器里那一句 `VarError -> case-stale` 定归因（契约写在 `resolve.ts` 顶部），而不是在等待那一侧再推一遍归因。

**修的时候顺手补了另一件反方向的事**：三条真超时分支里，`continue` 那一支是唯一**不带 `keyContext`** 的（`fail`/`error` 两支都带 `waitedMs` + `condition`）。这不是同一处缺陷的另一半，是相反的症状 —— 那一支今天确实判得对（真超时 + 作者容忍 = pass），只是"这轮过了"被当成了"没什么可记的"。后果不在那一行，在**聚合那一层**：看板要数"这一场有多少等待是等满超时后被放过的"，靠的是 `select(.keyContext.waitedMs)`，于是这个数**恰好漏掉全部被容忍的超时**，报出来像"几乎没有超时"。它只会往好看的方向偏，所以没人会怀疑它 —— 这是本节那条"少一件东西看起来像什么都没少"（`docs/08` §3）在**统计口径**上的形状，而不是在单条结论上。补的两个键与另两支**逐字同形**；刻意不补 `evalError`/`polls`：那一支走不到 `evalError`，而 `polls` 在三支里都没进过磁盘格式，不该为一条测试方便加字段。

#### 3.2.4 一次等待必须从头到尾问同一个问题

`vars` 里可以有 `{gen}`，而生成器的定义就是"每次求值给一个新值"。**每轮 poll 重算的话，一次 20 轮的等待会拿二十个不同的订单号去查数据库，而摘要说"数据库出现匹配行"—— 它从没查过那一个。** 所以绑定值经 `onceSqlVars` 每条条件只求值一次，缓存键是**条件对象本身**（一棵 `allOf` 树里可以有多个 `dbRow`，按类型名缓存会让它们共用一份绑定）。

缓存的生命周期是**一次 `waitUntil`**，两头都会坏：每轮重算 = 上面那个；跨 run 复用（模块级 Map）= 第二场跑起 `{gen}` 永远是第一场那个值。所以键是条件对象、生命周期是这次调用，一头挡一种。变异 **B3（旁路缓存）与 B4（按类型名缓存）各红各的测试** —— 缓存的**存在**与缓存的**键**是两条性质。

> B4 的第一版写错了：它把键换成一个每轮新建的对象字面量，于是缓存永不命中，行为与 B3 逐字节相同 —— 两个"不同的变异"其实在测同一件事。真正的"按类型名缓存"要连 `seen` 的声明一起换（`WeakMap` 存不了字符串键）。

#### 3.2.5 `.optional()` 而不是 `.default({})`：量出来的，不是选出来的

`canonicalScenario` 会把 zod 补出来的默认值**物化**进规范串，而 `stable()` 会丢掉 `undefined`。所以：

```
.default({})  → 每一个已有 dbRow / dataSource 场景的 irSha 都变（历史版本指纹全部作废）
.optional()   → 不写这个字段时逐字节不变
```

这一字之差把"修一个 bug"与"一次磁盘格式迁移"分开了，所以它**不能靠推理选定**，探数量完才写。两处（`waits.ts` 与 `steps.ts`）各有专门测试钉住那个选择（变异 B6/B7）—— **B7 第一轮 survived**，因为我只给 `dbRow` 写了那条，`dataSource` 那一处只在注释里断言了同样的性质。注释里的断言不算断言：它不会红，而人会相信它。

#### 3.2.6 静态那半边是 warning，不是 error

新增 `SQL_PLACEHOLDER_UNBOUND`（warning）。与 `HOVER_THEN_NOT_IMPLEMENTED`（error）刻意相反，区别在运行时的形状：

| | 运行时会怎样 | 所以静态该 |
|---|---|---|
`hoverThen` | 判 **pass**（假绿） | **error**，拦在跑之前 |
`$` 在 SQL 里 | 数据库拒 → 报错/超时（**会响**） | **warning**，只是想说早一点 |

已有场景全部是照着旧注释「`$var` 占位由引擎绑定」写的。把这条定成 error，等于用一次 lint 变更把别人的 CI 全停掉（`run --strict` 落 exit 3），去换一个运行时本来就会说的错。**静态闸该拦的是运行时看不见的错**，不是"运行时已经会说、只是想说早一点"。误报面（SQL 字面量里的 `'$100'`、`$$引用$$`）由摘要里那句"若是字面量请忽略"承担 —— 反过来收紧判据漏掉的是主流错法，两害取其轻。

#### 3.2.7 一条与扫描器能力边界的取舍

三个 `vars` 字段同名（这是刻意的：同一个 IR 概念在三处必须同名），使 `tooling/unread-fields.mjs` 的 `declCount>1` 判据对它们失明，`inconclusiveCeiling` 从 230 涨到 233。其中 `DbStepSchema.vars` **不是新增字段而是归因变差** —— 它先前算"读过"，被这次加的两个同名兄弟挤成"判不出"。这条差别写在 baseline 的 `_ceiling_comment` 里（"测量变准了"和"测量变瞎了"在数字上长得一模一样）。

**刻意没有为了扫描器好看而改名**（`sqlVars` / `bindVars` 能让扫描器归得出）：改名换来的是扫描器报表干净，代价是"这三处是同一件事"又得靠人记。扫描器的能力边界不该反过来决定 IR 的命名。

### 3.3 `capture` 在混合场景里取的是页面截图，不是设备截图 🔍

```ts
const uiOrDev = s.kind === 'navigate' || s.kind === 'act' || s.kind === 'capture' ? adapters.ui : adapters.device;
```

路由**按步骤 `kind`，不按声明的 target**。所以 `tap/input/swipe/key/app/logcat` 走 `adapters.device`（继承租约那台设备，对），而 `capture` 和 `assertPage`/`assertUi` 走 `adapters.ui`。

后果：`docs/02` §9 那条场景在 app 步里写 `before: { kind:'capture', mode:'screenshot' }`，Android 场景里存进证据的是**页面截图**（`adapters.ui`），不是设备截图。混合场景（web + app 同时在场）里，"截图"这个词有两种含义，而 IR 上看不出来是哪一种。

**注意别说成"路由错了"**：`kind` 决定端口本身是自洽的（`navigate`/`act` 只能是 Web）。缺的是**混合场景里没有第三个维度来表达"这个 capture 要哪一侧"**，而 `snapshotKind`（`docs/09` §1.2）已经证明这件事必须显式 —— 四种快照世界观不能靠步骤名猜。

**同一根因下还有一个更具体的对不上，而它的后果比 capture 坏一个量级**（这条也更好验证，因为两端都在仓库里）。三段事实，逐段附取证：

```ts
// ir/steps.ts   —— 权威表
assertPage: 'web',  …  assertUi: 'mobile',
// ir/steps.ts   —— 租约闸
export const LEASE_REQUIRED = ['app','tap','input','swipe','key','logcat','assertUi','manualHandoff'];
//                                                    ↑ 有 assertUi，没有 assertPage
// engine/assertions.ts —— 两者进同一个函数
case 'assertPage': case 'assertUi': return evalUiAssert(s, deps);
//   改前函数内：const adapter = deps.adapters.ui ?? deps.adapters.device;   ← 合流就在这行（已修，见下）
```

把这三段和 §3.4 的 `targetOf` 串起来，**"纯 app 场景里误写 `assertPage`"的真实走法**是：

| 步 | 发生什么 | 依据 |
|---|---|---|

| 2 | `needsWeb(scenario)` 因此为真 → **CLI 真的去建 Web adapter** | `cli/wiring.ts` 里 `if (needsWeb(o.scenario))` 那一处 |
| 3 | 没配 `ATEST_BROWSER_BIN` → **装配期就抛 `EXIT.ENV`(4)**，一次 run 都没起 | 同上那句"装配期报错，不进 run" |
| 4 | 配了浏览器 → `evalUiAssert` 里 `ui ?? device` **选中 `adapters.ui`** → 断言打在**页面**上，而这条场景根本没有页面 | `engine/assertions.ts` |
| 5 | 而 `ctx.target` 写的是 `'android'`（`targetOf` 落进"其余"那一支） | §3.4 |

**第 3 步和第 4 步是两个不同方向的坏**，而且都不是"报错说这条 IR 写错了"：

- **第 3 步**：一个纯 app 场景因为一个用错的 kind，要求你去配 Chrome。报错文案说的是"本次场景用到 Web 步骤，但没配浏览器"—— **字面没错，而它是这条 IR 缺陷能得到的最误导人的一句归因**：人会去装浏览器，不会去想"我这个场景里哪来的 Web 步骤"。

**修法只有一处，而我第一版写的另一个候选是错的**：我起初写了"① 把 `assertPage` 也塞进 `LEASE_REQUIRED`，顺势合并两个 kind"。**①是错的，写完 §3.5 才发现**：`STEP_TARGET` 明确分 `assertPage:'web'`/`assertUi:'mobile'`，`LEASE_REQUIRED` 只为 `assertUi` 要租约 —— 设计上是两个世界，**合流只发生在 `evalUiAssert` 那一行**。所以修法就是那一行：按 kind 分流，`assertPage` 只认 `adapters.ui`、`assertUi` 只认 `adapters.device`。（留这一段是为了记形状：**"两个候选都行"通常意味着我还没读到第三个事实** —— 这次缺的那个事实是 `STEP_TARGET`。）

### 3.4 运行时又抄了一份"kind → 端"的表，而且已经和 IR 那份对不上（`assertPage` 已实测 → ✅ 已修，见 §3.4.1）

IR 里**本来就有一张权威表**（`ir/src/steps.ts`）：

```ts
/** 步骤类型 → 所属目标端。用于 lint（跨端检查）、UI 图标、能力校验（docs/09 §1.1 约束 3）。 */
export const STEP_TARGET: Record<Step['kind'], 'api' | 'web' | 'mobile' | 'any'> = {
  ...
  navigate: 'web', act: 'web', assertPage: 'web', capture: 'web',
  device: 'mobile', app: 'mobile', tap: 'mobile', ..., assertUi: 'mobile',
  ..., db: 'any', ...
};
```

`deriveTargets()` 是它唯一的权威消费者，而 `cli/src/wiring.ts` 里把"为什么要用它的理由"写得非常清楚，值得整段引过来，因为**下一段就是它描述的那个事故**：

>  - 列一份 `['navigate','act','capture','assertPage']` 会一直"对"到某天新增一个 web kind，之后它安静地不再命中，症状是"新 kind 报 ui adapter 未注册"；
>  - STEP_TARGET 与 CHILD_KEYS 都在 IR，本层重抄一份就是本仓记过多次的"两处各一份，迟早只更新其中一处"。

而解释器里的 `targetOf()` 就是那份重抄（**下面是改前的形状，现已不是这样** —— 留在原位是因为下面那张漂移表与 §3.4.1 那几条都以它为对照）：

```ts
if (s.kind === 'device') return s.target;                    // 显式
if (['navigate','act','capture'].includes(s.kind)) return 'web';
if (['http','openapiCall','db'].includes(s.kind)) return 'api';
return (ctx.lease?.target as …) ?? 'android';                // 其余全部
```

对照 `STEP_TARGET`，漂移是现成的 —— **而本轮把"会漂到什么"跑出来了**（探针 `/tmp/atest-probe/probe4.mjs`，同一份 `git archive HEAD` 的临时编译产物；**spy 自己就是探针，`ctx` 是传进来的，记 `ctx.target` 不需要改任何测试夹具**）：

| 探针 | 场景 | adapter 实际收到 | 结论 |
|---|---|---|---|
| **P1** | 纯 app 场景（`device`+`assertPage`），ui 与 device **同时在场** | `{who: 'UI', target: 'android', kind: 'assertPage'}` | **两个坏同时发生**：断言打在 **UI** 上（`ui ?? device` 选中 ui，§3.3 第 4 步因此从"推的"变成"实测的"），而 `ctx.target` 记着 **`'android'`** |
| **P2 对照** | 同 P1 但用 `assertUi` | `{who: 'UI', target: 'android'}` | **两个 kind 收到的是同一个 adapter** —— 这是"合流"的直接证据，也证明 P1 那个 `who:'UI'` 不是 spy 认错人 |
| **P3** | **纯 Web 场景**（只有 ui adapter，`navigate`+`assertPage`） | `{who: 'UI', target: 'android'}` | **最坏的一条**：一个再普通不过的 Web 场景，没有任何跨端、没有任何配置问题，`ctx.target` 就是 `'android'` |

**P3 把我原来那句话证伪了。** 我写的是"今天没有别的平台 adapter 所以撞不到"——**错了**：不需要 iOS/鸿蒙 adapter，不需要混合场景，**纯 Web 场景里 `assertPage` 这一步的 `ExecContext.target` 今天就是 `'android'`**。它一直没被发现，只因为**没有任何 adapter 读 `ctx.target`**（`adapter-web` 的 `assertUi` 签名里那个参数是 `_ctx`，划掉的），所以它今天**是一个确实存在、但还没有消费者的坏值**。

**这恰恰是不能用"反正没人读"来结案的两种情形之一**：
- 说"没人读所以无害"→ 那就不该继续把它算缺陷，**而应该删掉这个字段或者把它做成必填且正确的**，否则 `docs/09` §1.1 约束 3 那句"能力探测决定路由"落地那天，第一个读它的代码就会拿到 `'android'`；
- 说"这是缺陷要修"→ 那 P3 这条探针的形状就是要补的测试，而它**只要一个 spy**（我上面三行就是全部成本）。
**我倾向前者一半 + 后者一半**：`targetOf` 里 `assertPage`/`capture` 这类**该进第三类而不是第四类**（一行改动 + P3 那条测试），而"没人读的字段"这件事本身记在 `docs/08` §3 那一族里，不必为它发明机制。

| kind | `STEP_TARGET` 说 | `targetOf` 实际给 | 后果 |
|---|---|---|---|
| `assertPage` | `web` | 落到"其余" → 没有租约 → **`'android'`**（**P3 实测**） | 断言走 `adapters.ui`（Web），而 `ExecContext.target` 写着 `'android'`。**证据、trace、adapter 三处会各自转述一件没发生过的事** |
| `db` | `any` | 写死 `'api'` | ~~目前无害（db 只有 api 侧能用）~~ → **本轮探针实测：`db` 压根走不到 `targetOf`**（它在 `execCtx('api', s.id)` 处直接给端），所以这一格不是"暂时同解"，是**死支**。写这份表的时候我把它当成"活着的错"，因为它看起来就在函数里 |
| 未来任何新 web/mobile kind | 表里加一行就够 | 静默落进"其余" | `wiring.ts` 那段预言的形状，一字不差 |

**这一条属于 `docs/14` §4.3 那一族，且是第一个"两处都有、都跑了、值还互相矛盾"的实例**（前面几个子类都是"一处有一处没有"）。它同时是 §3.1 里 `release` 写死 `execCtx('android')` 的同一个根：**运行时的 `target` 是从步骤种类现推的，而不是从 IR 那张表读的**。

**修法有一处不能 delegate，要说清**：`STEP_TARGET` 的 `'mobile'` 是一档、不区分 android/ios/harmony（`deriveTargets` 靠读 `s.target` 再细分），而运行时**恰恰需要**那个细分。所以正确的拆法是——**api / web / any 这三档去读 `STEP_TARGET`，平台那一维继续走 `stepCtx.lease.target`**。别整个换成 `deriveTargets(scenario.body)`：那是场景级的集合，回答不了"这一步在哪个平台上"。

#### 3.4.1 ✅ 已落地（本轮），以及落地时测出来的三件额外的事

改完的形状就是上面那句：`targetOf` 只剩 `device` 一行特例 + 查 `STEP_TARGET` 得 api/web + 其余走 `platformOf(slot)`（平台那一维的唯一实现，守望与它共用，见下面第 ③ 条）。**`?? 'android'` 这个兜底整个删掉了**，换成下面第 ① 条。

**① 加了一个取值 `'any'`，而不是给兜底挑另一个端。** `ExecContext.target` 的联合多了 `'any'`（`ExecTarget`），含义与 IR 的 `TargetRefSchema` 同一个词：**"这一步不属于任何一端"，不是"哪一端都行"**。加它是因为不加只剩两条路，而另一条正是本节记的那个错：算不出端时总得给个值，给任何真实端都是编。实测成本为零 —— 这个联合全仓只声明一处，没有任何 `switch (ctx.target)` 会被新成员打破，`TargetKindSchema` 是 IR 场景级 `targets` 在用（两者对不上是刻意的：运行时那一维要能表达"不属于任何端"）。
　**今天真正产出 `'any'` 的有两种形状**（原形状逐个探出来的是 `.scratch/probe-any-shapes.mts`，永久形态是 `adapter-contract.test.ts` 那两条）：`assertLlm`（`llm.judge` 收到 —— `evalLlmAssert` 是把 `deps.ctx` 原样递给模型的），以及 `world: "mobile"` 而**没有租约**的等待条件（mobile 对应三个真实端，只有租约知道是哪个，没租约时这里只能报'算不出'）。**`assert` 与 `assertPerf` 不会**：那两个分支只读变量、压根不碰 `deps.ctx`（读 `assertions.ts` 确认，不是"没测出来"）。
　**这一格原本写的是"只有一种形状"**，是我从"纯 Web 的 wait"那一条探针推的；补一条探针扫别的 any 档 kind 才发现 `assertLlm` 也算 —— 与本轮反复撞的那条同一条：**从一例推出来的"只有"，要先扫完这一类**。
　这两种形状**各有各的测试**（`adapter-contract.test.ts` 里「算不出端时 ctx.target 是 any」与「assertLlm 送给模型的 ctx 同样是 any」），理由不是 `'any'` 这个值多对，而是**联合里多了一个成员而没有任何测试产出它，那这个成员就是不可证伪的**：下一个人分不清那是设计还是漏填。　**这两条从前钉的是另外两个形状**（纯 Web 的 `wait` 步 + assertLlm），等待条件补上 `world` 之后第一条红了 —— 那是那条测试注释里预先写下的预言兑现，不是回归，换形状的理由与过程记在 §3.6 末尾。**分成两条这件事本身也由此有了实证**：世界字段那次改动只弄红了一半，另一半原样绿着。

### 3.6 `needsWeb` 只看 `body`：同一条断言换个数组，就换一整个世界（已实测）

> 这一小节原先挂在 §3.3 底下（标题是"顺手记一条"），**那是错的归档**：它讲的不是 `capture`，而是"目标端推导只看一个数组"，与 §3.3 只是同处一段代码。本轮测完它的后果之后，它比 §3.3 整节都重，不该再当附注。

判据只有这一行：

```ts
export function needsWeb(scenario: Scenario): boolean {
  return deriveTargets(scenario.body).includes('web');   // ← 只看 body
}
```

`setup` / `teardown` **不在判据里**。而这不是某人漏写 —— 顺着查下去，**"目标端只看 body" 是 IR 自己的约定**：

```ts
// cli/wiring.ts        —— 要不要建 Web adapter
return deriveTargets(scenario.body).includes('web');
// ir/index.ts 的 withDerivedTargets —— 场景的 targets 字段本身
return { ...draft, targets: deriveTargets((draft.body as Step[] | undefined) ?? []) };
```

于是同一个 `navigate` 步骤：**写在 `body` → 建 Web adapter；写在 `setup` → 不建**，运行时才报"ui adapter 未注册"。**这一句我原样写了很久，而它只对 `navigate` 成立 —— 对 `assertPage`，本轮实测到的后果更坏，且不报错**：

| 探针 P4 / P6（**全部是改前的实测**；下面 ✅ 那条之后 `ui ?? device` 这行回退已经没了） | 纯 app 场景（`device` 租约在 `body`），差别只有 `assertPage` 放哪个数组 | |
|---|---|---|
| | `assertPage` 在 **body** | `assertPage` 在 **setup** |
| `deriveTargets(body)` | `['android','web']` | `['android']` |
| `needsWeb`（`cli/wiring.ts` 里那个 `if` 原样调用） | `true` → 装配 `ui` + `device` | `false` → 只装配 `device` |
| `evalUiAssert` 里 `ui ?? device` 选中 | **UI**（Chrome / ARIA 世界） | **DEVICE**（uiautomator / hierarchy 世界） |
| 那一步自己的 `status` | **`pass`** | **`pass`** |

**两侧都 pass，而它们测的是两个不同的世界。** 这才是这一小节真正要留的东西：

- `navigate` 那一类"漏装配"是**响**的（探针 P7 实测：`navigate` 写 setup → 那一步 `error`，摘要 `navigate 需要 ui adapter`）—— 难看，但会说话；
- `assertPage` 这一类是**静默换 adapter** —— 因为 `evalUiAssert` 那行 `ui ?? device` 恰好让另一个 adapter **顶上来了**。一个断言在 Chrome 里查 ARIA，和同一个断言在安卓上查 uiautomator 树，**语义完全不是一回事，而结论都叫 pass**。

`docs/14` §4.3 那一族里，(b)"读了但用错"讲的是**值**错；这条是**执行对象**错。判据的覆盖范围（只看 `body`）与被判对象的可选位置（三个数组）不一致，中间还隔着一个"另一个 adapter 顶上来"的容错 —— **少任何一环都不会静默**：如果 `evalUiAssert` 是严格取 `adapters.ui`，第 4 行就会是 error 而不是 pass，这条就只是普通的配置报错。

所以修这条**不能只改 `needsWeb`**（改完 `navigate` 那类会好，`assertPage` 那类只是不再换 adapter、但仍然打在错的世界里）。要一起动的还是 §3.3 那一行：**`evalUiAssert` 按 kind 分流**。分流之后，setup 里那个 `assertPage` 立刻变成"这条场景没有 Web adapter"的 error —— 归因正确，且**上表最后一行那两个 pass 自动消失**。

**✅ 两半都已落地**（`evalUiAssert` 按 `STEP_TARGET` 选端口 + `needsWeb` 走三层）。测试 `packages/engine/test/ui-assert-world.test.ts` 与 `packages/cli/test/wiring-web.test.ts` 里 setup/teardown 那条；变异 `tooling/mutate/ui-assert-world.json`。**条数照例不写在这里**（本文档开头那条纪律）。

分流判据取的是 IR 里那张 **`STEP_TARGET`**（`assertPage: 'web'` / `assertUi: 'mobile'`），**没有按 `assertKind` 分区** —— 上面那句"按 kind 分流"写得对，而我**动手时**的第一反应其实是去切 `UI_ASSERT_KINDS`（哪些谓词是 web 专属、哪些移动端专属），因为那串常量就贴在断言 schema 上、看着正是这件事的入口。读代码时才发现**根本不用切**：端已经写在**步骤 kind** 上了，而且是 lint 与 `deriveTargets` 共用的那一份权威表。按 assertKind 切会造出第二份"谁属于哪一端"的表，而两份表迟早只更新其中一处。
> **`url` 这个 assertKind 在两堆里都能待**，就是"按 assertKind 切"走不通的具体例子：`assertPage{url}` 查的是浏览器地址栏，`assertUi{url}` 查的是 app 当前路由 —— **同一个谓词名、两个世界**（`UI_ASSERT_KINDS` 是两者共用的一份枚举，`adapter-contract.test.ts` 里就有一条 `assertUi` + `assertKind:'url'` 的用例）。分区表无论把它放哪一边都错另一边。分区方案当场作废。
> **形状**：入口那个"看着正是这件事的答案"的常量（这里是 `UI_ASSERT_KINDS`），与真正的答案（`STEP_TARGET`）隔着两个文件，而前者名字更贴切。**名字贴切不等于它是权威表** —— 这一条与 §3.8 那条"从调用参数表推行为"是同一个毛病的双胞胎：都靠"看起来"省掉了查证。

**修的时候实测到的第二条比文档里那条更常踩**：上表记的是"`assertPage` 没有 ui 时被 device 顶上"，那需要场景**缺**一个 adapter；而 `assertUi`（移动端档）在**两个 adapter 都在**时永远打 UI —— 混合场景（web + app）本来就两个都在，所以**移动端的断言一直在由浏览器执行、一直绿**（永久落点 `ui-assert-world.test.ts`「assertUi（移动端档）两个 adapter 都在时打 device，不打 ui」）。探针四行输出（`.scratch/probe-uiassert.mts`；**改前错的是第 2、3 行**，第 1 行本来就对、第 4 行前后一样，我把"三行错"写进去过一次又划掉 —— 一个数字顺手写大，下一个人就会怀疑整张表）：

它注释里写的就是"绕开租约闸"这件事，上面那个探针只是它的来历，不是它的落点）。

**刻意没有顺手改的第三处，现在改了**：`wait.ts` 里那三处同形状的 `??`（`uiPredicate` / `uiIdle` 是 `ui ?? device`，`template` 反过来是 `device ?? ui`）。当时不改的理由是真的，而且不是懒：**那三种等待条件在 IR 里压根没有端** —— `STEP_TARGET.wait === 'any'`，条件对象里也没有任何世界字段，`ExecContext.target` 又只能来自租约（纯 Web 场景里没有）或兜底。也就是说「该用哪一路探针」这句话**没有原料**，硬改只能靠猜。
　**原料后来补上了**：`uiPredicate` / `template` / `uiIdle` 各多了一个可选的 `world: 'web' | 'mobile'`（`ir/src/waits.ts`，docs/02 §3），三处选择收敛成一个 `resolveWaitWorld`。当时那句「它今天选对了是因为只有 ui 在场，不是因为判断对了」现在反过来成立：**判据只有一份了**，所以这一族的变异也从三条变成一条（`mutate/wait-world.json` 顶部记了这笔账 —— 「同一个坏法要变异三次」本身就是那个坏抄了三遍的证据）。
　**改完之后仍然要说清剩下的那半**：`world` 是 `.optional()`，混合场景里不写就是**不知道**，那时引擎报 `case-stale` 而不是替作者挑一个。所以「作者没写」这条路今天是**报错**，不是被猜对了 —— 这个区别对使用方是实质的：前者会让人回去把 IR 补上，后者会让人以为自己写对了。

　**哪些行今天走不到，先说清（沿用 §3.4 给 `targetOf` 记死支的那个规矩）**：本轮最核心的那条判据 —— 两档都在场而作者没写 `world` ⇒ 报 `case-stale` ——**在 CLI 装配出来的场景里今天到不了**：`wiring.ts` 压根不装配 `adapters.device`（ADB/iOS/鸿蒙那半边没开工，docs/14 §5），所以真实运行里最多只有一个槽位在场，永远走的是第三条判据（只有一档在场就用它，行为与改动前逐字相同）。**这不是把没用的东西留着**：那条报错是这条决定的**全部代价**所在 ——「不许猜」这件事只有在两个选项都摆在桌上时才需要被执行，而设备侧 adapter 一接上那一天立刻就到；等到那时再补判据，就是让第一个混合场景的用例结论由装配顺序决定。永久形态是 `wait-world.test.ts` 前几条（直接给两个槽位，绕开 CLI 装配）+`mutate/wait-world.json` 的 W1。**它今天靠测试活着，不靠生产路径活着** ——这句话要说出来，否则下面那个 ✅ 会被读成「线上正在这么判」。
　**而补上 `world` 之后紧接着暴露的第二格是「转述」，这一格是读代码时没预见到的**：探针选对了，`ExecContext.target` 却仍然是解释器按 `targetOf(step)` 算的那个值，而 `STEP_TARGET.wait` 是 `'any'` —— 于是**条件里明明写着 `world: "web"`，adapter 收到的是 `'any'`（纯 Web 场景）或者租约上那个平台**（混合场景里一句「问浏览器」的探针，转述出去是 `'ios'`）。这是缺陷类 (d)「有字段、有判据、没有面向人的载体」的 **adapter-facing 版本**，与 §3.4 修掉的 assertPage P3 同形，区别只在载体是 `ctx` 而不是报告。今天没有任何 adapter 读它（`adapter-web` 那个参数是划掉的 `_ctx`），而「碰巧没人读」推不出「值是对的」—— 那句原话就是本节写的。
　　解法是让 `resolveWaitWorld` **一次交出 `{ adapter, ctx }`**：两个载体由同一次调用给出，「用 web 那一路探针而 ctx 里写着 ios」这个组合在结构上写不出来。**`mobile` 那一档刻意不改写 ctx**（原样透传租约平台），这个不对称要有答案：`web` 在 `ExecTarget` 里是一个确定值，`mobile` 对应 android/ios/harmony 三个真实端而**只有租约知道是哪个**，从 IR 这一侧填任何一个都是编（`mutate/wait-world.json` 的 W10 就打这个）。

　**这一处改法让一条既有测试红了，而它红得对** —— 值得单独记，因为这种红很容易被当成回归处理掉。`adapter-contract.test.ts` 里「算不出端时 ctx.target 是 any」那条的注释早就写着「如果哪天决定给等待条件补上世界字段，这条会红，那时该改的是这里」；补上之后**它果然红了**。处理不是删掉：它钉的是「`ExecTarget` 里那个 `'any'` 成员有真实生产者」（没有生产者的联合成员不可证伪，下一个人分不清那是设计还是漏填），而这条理由与用什么形状无关；所以换一个 `'any'` **仍然是诚实答案**的形状 —— `world: "mobile"` 而没有租约。
　　可记下的一般形式：**预先写下的预言红了是好事，但它只在作者认得出来的时候才是好事**。认不出来就会当成回归改回去，于是那条护栏连同它的理由一起消失。所以这种预言要写在**它自己那条测试的注释里**（改的人一定会读），而不是只写在设计文档里。

**修法（两处，一次做完）**：`walk(scenario.body, …)` → `walk([...setup, ...body, ...teardown], …)`，**同时** `leaseAcquiredAt` 的推进要跟着换索引，并且 `scenario.targets.some(...)` 那个前置条件要改成看三层（否则修了 walk 也只是把 B 那半边修好）。**顺序有讲究**：只改 `walk` 不改 `targets`，A 的误报会扩大到"setup 里放 device、body 里放 device 之前的 tap"这种现在不报的组合 —— **半修比不修更容易让人以为已经对了**（这一族本仓记过不止一次）。

**为什么这比"一处漏写"值得记 —— 而且我上一段差点写错**：`lint.ts` 里的 `walk` 调用**大多**写 `[...setup, ...body, ...teardown]`（现场数：`grep -c '\.\.\.scenario.setup' packages/engine/src/lint.ts`，**不钉数字** —— 那个数每加一条 lint 都要动，一旦烂掉，下一句"只看一层"就显得像笔误），**而独独"逐步骤规则"那一大块走的是 `walk(scenario.body, …)`**。我第一版写的是"每一处都看三层"——**那是被 grep 的数量骗的**：数到的那些拼接全在别的规则里，而出问题的那一块不在其中。**"大部分都对"和"都对"读起来一样，害人的正是差的那一个。**
后果范围比 `RESOURCE_LEASE_MISSING` 一条大：**整个"逐步骤规则"块都在 body 里跑**（`grep -o "code: '[A-Z_]*'"` 圈出这一块推的规则：`ASSERT_FREE_STEP` / `RESOURCE_LEASE_MISSING` / `SLEEP_USED` / `LOOP_UNBOUNDED` / `CLEARDATA_VS_PRESERVE_SESSION` / `LITERAL_OVERFIT` / `TEMPLATE_*` / `VISION_STEP_IN_CI_GATE` 等）。**`setup` 里的裸 `sleep`、`teardown` 里没有断言的写操作，今天一条都不报。**
`walk` 自己只认 `CHILD_KEYS`/`cases`，三个数组是各调用点自己拼的 —— **别把 `walk` 当成它会自动看全三层**。

⚠ 但**别把这句读成"所以那些规则都该看三层"**：`orderIdx` / `leaseAcquiredAt` 这类**跟顺序有关的判据**，扩到三层要重定义顺序（`setup` 先于 `body` 先于 `teardown`，那是运行顺序，不是数组拼接顺序），而"teardown 里一个 `sleep` 该不该和 body 里一个 `sleep` 同罪"是个产品问题不是 bug。**本轮只坐实了 `RESOURCE_LEASE_MISSING` 这一条**（上表 A/A′/B/C），其余那些是**同一片代码暴露出来的待查范围**，不是已确认缺陷 —— 这个区别不写清，下一轮就会有人拿这张表当 checklist 一次性改完，把产品问题当 bug 修掉。

归类要说准：**这是 §4.3 子类 (b) "读了但用错"的一个实例，错在覆盖范围**。我第一版把它写成"那个族的第四个子类"——**错了两次**：那一族已经有四个子类（(a)–(d)），要加也是第五个；而它根本不是新形状。那一族的轴是"这个字段谁来读、谁能发现没读对"，本条的轴是"判据覆盖了三个步骤数组里的几个" —— **同一个缺陷类不等于同一个子类，硬编号会让下一个人以为有一套五种防法**。
（这一族与"跨端事务"严格说不是同一主题，**但它必须留在这份文档里**：它的全部后果只有在"一个场景同时可能有 web 与 mobile"时才显形，而那个前提正是本文的主题。**该不该顺手把 `docs/02` §6 那条 lint 清单也补一句，等 §5.1 那两条变异落地之后再说** —— 现在补，写的还是"待查范围"而不是结论。）

### 3.7 取消这条链路：`EXIT.ABORTED` 有名额而执行侧没人兑现，以及"每一层都对"的三段漏接（已实测）

这一节讲的不是跨端，是**跨层**：一次 Ctrl-C 与"流水线里的退出码"之间隔着五层，而它曾在这五层里**断了三次**。放在这份文档里是因为它和 §3.6 是同一条判断的另一种形状 —— **每一层单独读代码都得出"这里没问题"**。

**缺陷类的归属先说清**：这是 `docs/14` §4.3 子类 **(c)「读了、也判了，但没有生产者」**换到**对外 API** 这一层上的复现，**不是第五个子类**。以前那例是"IR 字段有、引擎判了、adapter 不报数"，这里是"码表有名额、门禁判了、执行侧没人返回"；同一子类、不同表面。（`docs/14` §4.3 表下那段讲的是为什么硬编号有害，`exit.ts` 里那句"10 = 我清理干净了 / 130 = 我没有"讲的是这两个码各自的意思。）

**改动前的形状**（三处都是本机跑的，引号里是原始输出）：

| 断点 | 位置 | 实测到的形状 |
|---|---|---|
| **① 没人接信号** | 各包 src 里 `process.on`/`addListener` **零命中**，`runOptions.signal` 没有生产者 | 引擎那句 `opts.signal?.aborted` **恒读不到 true**。`EXIT.ABORTED = 10` 定义着、`CI_HINT` 印着"10 被中断"、`WORSE_ORDER` 给它排了序，而**全仓没有一条路径返回它** |
| **② 中断了不跑 teardown** | `runScenario` 的 teardown 只挂在 `try` 后半段 | `status = pass  results = seed:pass, slow:pass  teardown 跑了吗 = false`。**环境里留下这次 run 造的数据，而报告/trace/证据包里零痕迹**（`TEARDOWN_FAILED` 也挂在 try 里，所以那句也不发）。而按一次 Ctrl-C 是最常见的取消 |
| **③ 装配层拿到 flag 却没交给引擎** | `cmdRun` → `runOne` → `assemble` 之间少一跳 | **`退出码 10` 而证据包叫 `evidence.sig1.pass.zip`** —— 码是对的（那个 10 来自"后面的场景被跳过"），产物说"正常通过"。只看退出码会以为接线成功，只看文件名会以为是 store 的问题 |

**③ 是这一族里最难发现的一种**，因为它**给出了一个正确的退出码**。三段漏接各有一个专属测试，别的测试抓不到：

- ① 由 `packages/cli/test/signal.test.ts`（单元测试 + 一条端到端）与 `tooling/mutate/signal.json`（P1–P16）钉；
- ② 由 `packages/engine/test/interruption.test.ts` 里"被取消的 run 里 teardown 照跑"与"超时砍断的 run 里 teardown 也照跑"**两条**钉 —— **两条不是冗余**：只把 `signal` 那一支绕开、不暂停**整道** run 级闸的话，清理第一步照样被 run 级超时抛死，而取消那条**照样是绿的**（变异 P2 专门测这个半修）；
- ③ 只能由**端到端**那条钉。单元测试测的是相邻两层，恰好测不到"这两层之间有没有接上" —— **而这一族缺陷的本名就是"层与层之间没接上"**（变异 P5）。

**还有一条"删掉一行而其余测试全绿"**：`cmdRun` 里"被取消挡掉的场景要进退出码"那一行（变异 P8）。原因是端到端那次取消落在 run **中间**，`report.aborted` 有值，10 由**门禁**给，那一行从未单独决定过退出码。补了一条"取消落在**两个场景之间**"的测试之后它才被抓住 —— 那条里跑完的场景自己完整（gate 给 0），于是那个 10 **只能**来自"有场景被跳过"。这条的形状值得单独记一句：**一段写着、注释详尽、没有任何测试经过它的代码**，是这一族缺陷最省事的产生方式。

**第四个断点是本轮读 §3.1 时顺手撞出来的**（变异 P16）：`runScenarioIn` 把 `secretResolver` / `envRevision` / `callStack` / `responseLedger` 一个个都透传了，**唯独 `signal` 没传**。实测：子里 6 条 sleep、第 3 条后翻 flag ⇒ `子场景跑了 s1..s6`，而父报告同时写着 `aborted = 外部取消` —— **人已经按了 Ctrl-C，深层 `call` 里剩下的步骤照样跑完**。子场景 body 里可能是 POST/下单/删除（`docs/02` §5 的不可逆动作纪律），而取消的全部意义就是**从此不再产生副作用**。
**修法因此不只是补一行**：`signal` 在 `runScenarioIn` 的参数上是**类型必填、值可为 undefined**，抄的是同一签名里 `responseLedger` 那条的做法 —— "忘了接"回到编译错误，而不是留一条要靠测试去追的静默分叉。**同一个签名漏同一个字段**，说明"哪些东西必须透传"这件事从来没被当成一个问题问过。

**几处刻意的不修，别读成遗漏**：

- **第一次信号只置标志、不当场死**。Node 看到"SIGINT 有处理器"就把默认行为换成"跑我们的回调然后继续活着"，这里把"活着"用满：当场死的话①没有产物②没有 `report.aborted`（10 又变回没人返回的码）③没有 teardown④不还设备租约 —— **手工按一次 Ctrl-C 就白占一台真机**。第二个**同名**信号才摘掉处理器、用同名信号打死自己（`128+signum`）；**摘在 kill 之前是必须的**，处理器在场期间进程对该信号免疫，不摘就"按多少下都出不去"。
- **异名信号不算"第二次"**。CI runner 取消任务常见的是"先 SIGTERM 几秒后补 SIGINT"，那是**同一句"停下"说了两遍**，不是"别收拾了"。混成一个触发条件的代价是**每次 CI 取消都丢掉清理**（变异 P10 专防这条）。
- **`report.status` / `manifest.status` / JUnit 计数被中断时都不改**。它们说的是"已完成步骤的结论"，那是真的 pass；改成 error 等于伪装成"某一步坏了"。`aborted` 是**关于报告**的事实，不是关于某一步的状态。产物侧那五份（summary 首行、manifest、包文件名、HTML 横幅+徽章、junit properties）各自独立钉住，读者各不相同 —— 变异集 `tooling/mutate/artifacts.json`（8 条，全抓到）。
- **取消的 run 里 teardown 跑完，但整体结论不改**，脏数据靠 `TEARDOWN_FAILED` 那一行说得出声（"少验了什么要有一行可指"）。
- **处理器里没有 await、没有 spawn、没有第二遍 run**。任何"再跑一遍/换个进程跑"的想法都会**重新发一次场景请求**；一次取消绝不该产生第二遍副作用。清理期间的等待靠"第二次同名按键"这个逃生门。

**仍然没有的东西**：`Lease.state` 的四态没有任何判据（§3.1），所以"取消时设备处于什么状态"今天说不出来 —— 归还动作做了，归还之后那台机器是不是干净，契约有四态而没人判定。

### 3.8 `parallel` 的分支共用同一个租约槽：一份全绿的报告漏掉一台真机（已实测、已修）

排在 §3.1 后面而不是并进 §3.1，因为 §3.1 讲的是"**租约该还的时候没还**"这一族生命周期，
而这一条是"**并发让一个本来对的还法变成漏还**"——同一个字段、不同的缺陷形状。

**症状**（`.scratch/probe-parallel-race.mts`，跑的是修复前的代码；
"两台都要还、还的是自己那台"今天的永久落点是 `lease-lifecycle.test.ts` 里同形状那一条）：一个 `parallel`，
两支分支各自 `device` + `tap`：

```
调用序 = lease:L1 → lease:L2 → perform → perform → release:L2
lease 2 次   release 1 次   收尾手上还攥着 1 台
父结论 = dA:pass, dB:pass, tA:pass, seqA:pass, tB:pass, seqB:pass, p:pass   整场 pass
```

**两份租约、一次归还。** 而且报告全绿、`p:pass`、没有任何一行说漏了什么。
在真设备农场里这是**持续累积的资源泄漏**：每跑一次这种场景少一台可用机器，
而 CI 是绿的，所以没有人为它停机 —— 恰好是本仓反复记的那族
"**看起来有防护，实际漏一个**"，只不过这次漏的是硬件。

**根因**：租约挂在 `runScenario` 的闭包变量上，而 `runStep` / `dispatch` / `runChildren`
都是那个作用域里的闭包 —— `parallel` 的分支**共用同一个槽**。于是两支里各一个 `device` 步
时，两边都看到"手上已有租约"，都走进"第二个 device 步先还前一个"那支逻辑，
**各自去还同一个 id，而自己新拿的那台谁都不还**。

那个"先还前一个"的逻辑本身是对的（§3.1 表里那一行，上一轮刚修的），
测试也是绿的（`lease-lifecycle.test.ts` 第 8 条，顺序场景）。
**它只是在并发下不成立** —— 一个"检查后再写"的模式在两个写者面前不是原子的。

**第二条后果更容易看漏**（`.scratch/probe-parallel-b.mts`；改后这一形状恒为 error，
永久落点 `lease-lifecycle.test.ts`「parallel 一支 device + 一支裸 tap → 裸 tap 那支**恒为 error**」）：一支 `device` + 一支裸 `tap` 时，
裸 `tap` 那支**能不能看到租约取决于谁先跑到** —— 实测两种结果都出现过（先跑 error、
后跑 pass）。同一份冻结场景两种结论，直接违反 `docs/02` §9 的确定性，
也正是 `useIdentity` 在 `parallel` 里被**直接拒掉**的同一个理由。

**修法**：每层作用域一个**租约槽** `LeaseSlot { lease?, owns }`。
- `parallel` 的每支分支 `newLeaseSlot(slot.lease)`：**继承**当前这一层手上那台，但 `owns: false`；
- `device` 步只有在 `slot.owns` 为真时才还手上那台（**借来的不还** —— 还了就是把上层
  正在用的设备扔回池子，那比漏还更难查，因为报告看起来连贯）；
- 分支自己申请的，在**分支结束**时还（不等整场跑完：那个槽随分支一起消失）。
- `runStep` / `dispatch` / `runChildren` 的 `slot` 形参**必填、无默认值**。默认值
  （`= runSlot`）我第一版写了，看着无害，但它让"新增一处嵌套调用忘了传"**编译得过而行为静默
  回落到外层槽** —— 正是这条缺陷的形状。留默认值等于把坑原地留着。

**删掉默认值没能防住这条缺陷的第二半年份，这一条比上面那段重要。**
`dispatch` 的 `parallel` 那一支写的是 `newLeaseSlot(runSlot.lease)` —— 从**闭包**里读整场那个槽，
而不是用它自己的形参 `slot`。顶层形状下 `slot === runSlot`，两种写法逐字节相同；
**嵌套一层 `parallel` 就跳过中间那一层**。改前实测（`.scratch/probe-nested-parallel.mts`）：

```
parallel P 的 A 支 = sequence[ device dA, parallel Q[ 裸 tap tInner ] ]，顶层无租约
调用序 ["lease L1","release L1"]   tInner:error「执行设备步骤前缺少 device 租约」
```

上面那个围栏里只有运行侧的输出 —— lint 那一半（**同一形状 lint 不报 tInner**）
是另一次探针（`.scratch/probe-nested-lint.mts`）量的，不是这段输出里印出来的，
所以不混在一起。它今天的永久落点是 `lease-scope.test.ts` 的 L6，
它钉的就是"内层该继承外层那一支"。

即"外层那一支刚申请到的那台，它自己的内层分支看不见"，而静态侧认为它该看得见 ——
**静态闸与运行事实又不一致了**，而且是在上一轮"这条修完了"之后原地出现的第二次。
这一族的两个方向也都齐了：上一轮是**多共享一层**，这一轮是**少继承一层**。

> **`slot` 必填只保证"这里传了个槽"，不保证"传的是传进来的那个槽"。**
> 我上一轮删默认值时写的理由是"编译器能逼每个容器写 slot"—— 那句是对的但不够：
> 它逼不出 `slot` 与 `runSlot` 的区别，而这两个标识符在同一个作用域里都合法。
> **签名能守的边界比我以为的窄，这一族最终只能靠嵌套形状的测试守**
> （`lease-lifecycle.test.ts` 末两条 + `lease-scope.test.ts` 的 L6；
> 变异 `T8`（运行侧）与 `S8`（lint 侧）互为镜像，两条都只有嵌套能抓）。

**少继承一层的症状只有继承缺失，归还一条都没坏** —— 这点我也先猜错过。
我原本以为会看到"内层还了外层那台的 id、同一台被还两遍"，探针
（`.scratch/probe-nested-b.mts`，把缺陷写回后跑）给的是
`lease L1..L4 / release L3,L4,L1,L2`、收尾手上 0 台：**归还全对**。
所以"看 id 集合是否相等"那组断言对这个缺陷是**瞎的**，能抓它的只有"继承到底成不成立"这一条断言。
**推出来的机制没跑过就是没跑过** —— 测试注释里那句"内层会还掉外层那台"已经写下去了，
是探针把它划掉的。

**修法必须连带 lint，否则造出一条新的"静态闸与运行事实不一致"**（本仓最贵的那一族）。
`RESOURCE_LEASE_MISSING` 原来是一条**整场单调的游标**（"先前见过 device 就算有租约"），
配上分支并发就给出相反判定，实测（`.scratch/probe-parallel-lint.mts`；
永久落点 `lease-scope.test.ts` 的 L1，它一次覆盖**两种声明顺序**）：

| 分支声明顺序 | 旧 lint | 运行时（修复后） |
| --- | --- | --- |
| `[device,tap]` 在前、裸 `tap` 在后 | **放行** | 裸 tap 那支恒 error「缺少 device 租约」 |
| 裸 `tap` 在前、`[device,tap]` 在后 | error | 同上 |

也就是说**旧判据让一件事取决于分支怎么写，而其中一种是假的：一份 lint 全绿的 IR 跑起来必红。**
判据因此改成作用域感知（`walkLease`），并且 `if` / `switch` 顺带一起修 ——
同一条推理：`then` 与 `else` 互斥、`cases[i]` 与 `default` 互斥，
"走 then 才拿到的那台"不能冒充"一直都在"。

**这条判据我自己写错过一次，值得记**：第一版把 `parallel` 的"一段"写成了整个 `steps` 数组，
于是两支被当成**顺序执行**，"A 支的 device 喂给 B 支"这个误判**原地留着没修掉**
（实测 P4 形状照样放行）。写第二版时才对着探针表逐形状重测发现。
**判据写错最难发现的地方就在这：它对大部分形状是对的，只有跨分支那一种坏，
而那恰好是它存在的理由。** 变异 `S3` 就是专门把这段改回去的。

**还有一条更阴的自我欺骗**：我写的 L4 那条测试**抓不到 `every` → `some` 这个变异**。
它的断言是"这份 IR 该报 RESOURCE_LEASE_MISSING"，而那个场景里 `else` 分支有一个裸 `tap`，
它在"进入容器时没租约"那条判据下**无论如何都会报** —— 于是断言恒真，对那个变异是**空转**的。
补了一条 L4b：场景里除了容器之后那个裸 `tap` 之外**不留别的裸设备步**，
这样"报不报"只由"容器之后有没有"这一个判据决定。
**"这条测试红了"与"这条测试能红"是两件事**，前者要靠变异证明，后者靠读代码感觉。

**顺带修掉的第三条**：`runScenarioIn` 的参数表里挂着 `ctxBase` / `execCtx` / `stepCtx` / `depth`
四个，函数体里**一个都没读**（逐个 grep：`a.ctxBase` 等各 0 次命中）。
`call` 那一行的实参老老实实写着 `stepCtx`（改名前），于是任何人读到那一行都会得出
"父的 stepCtx 传进子运行了"，进而以为父的租约在子里可见 —— **而它压根没被用**。
**"看起来传了"比"根本没这个参数"坏得多**：前者要读完整条链路才能推翻，后者一眼可见。
§3.1 里那句写错的"`parallel` 不共享 `stepCtx`"（本轮已改口，见那里第 3 条）
和这个误读是**同一个推理错误：从调用参数表推行为**。四个参数已删。

**取证**：
- `packages/engine/test/lease-lifecycle.test.ts` 最后六条（两支各 device / 一支 device + 一支裸 tap /
  外层租约被两支共享 / 嵌套时内层继承外层那一支 / 嵌套每支都自备租约 / 夹具自身的 id 陷阱）；
- `packages/engine/test/lease-scope.test.ts` 的 L1–L6（lint 侧，含两种声明顺序同判、嵌套继承及其反向对照）；
- 变异集 `tooling/mutate/lease-slot.json`（9 条：8 抓到 + 1 条刻意等价）与
  `lease-scope.json`（重写一遍，8 条：7 抓到 + 1 条刻意等价）。
  两份都是**逐条实跑过**的（`node tooling/mutate.mjs <spec>`），不是"看着能抓"。

**夹具自己骗过我一次**，也记在这里：设备农场夹具写的是
`n++; await wait(5); return { id: `L${n}` }` —— 两支并发进来时 `n` 已经都是 2，
两支各自拿到 `L2`，于是归还序列打成 `release:L2, release:L2`，
**看起来像"引擎把同一台还了两遍、另一台没还"**，而引擎其实是对的。
夹具造假 id 的坏处不只是误报：**它会让人去修一个不存在的缺陷。**
真实设备池发号一定是"申请成功那一刻"定下的。

**仍然没解决的一件事**（别读成已解决）：分支**并发**时"一支先 `device`、另一支后跑"，
运行时后者**有可能**看到前者那台（槽是在 `worker()` 里现取的）。
lint 不跟着这个不确定性走 —— 判它 error。于是这一形状是**假阳性方向**的偏差：
作者会被要求"给这一支自己加一步 device"。这是**故意**选的方向 ——
假阳性的代价是多加一次申请、结果不变；假阴性的代价是 CI 偶发红。
而那个"可能跑通"本来就不该被依赖：它由调度顺序决定。

## 4. 一条能跑的跨端写法（与 §9 那条例子的差异）

`docs/02` §9 那条是**目标形态**。在今天的代码上真能跑通的写法要改三处，每处都对应上面一条：

| §9 里的写法 | 今天 | 该怎么写 |
|---|---|---|
| `dbRow.sql` 内嵌 `$.mk.resp.data.orderId` | 🔍 占位不替换 → 每轮 SQL 报错 → 超时 | 先 `db` 步（它绑）+ `assignTo`，或用 `httpStatus`/`response` 条件等接口回来 |
| `assertUi.contains: "$.mk.resp.data.orderId"` | 待核：`evalUiAssert` 把 `s` **原样**交给 adapter，不做 ref 解析 | 稳妥写法：`assert{against:'$.mk.resp.data.orderId'}` 先落到一个变量，再让 UI 断言读那个变量；别在 `contains` 里写路径 |
| 设备步骤靠 `device` 步拿租约、后面隐式继承 | **本层内**继承可用（`setup`/`body`/`teardown` 之间也通），生命周期已接（过期会续、异常也会还）；**但不跨 `call` 边界**，见 §3.1 末段 | 子场景要动设备就**自己写一个 `device` 步**（今天 lint 也是这么判的）。`leaseMs` 现在会交给 adapter，但"到点自动还"仍由设备农场那侧负责，`teardown` 里别依赖设备 |

三端共享变量空间**这一半是真交付了** —— `$.<stepId>.resp.<path>` 在 API 步与 Web 步之间是通的，`parallel` 并回也有确定性规则。上面这三格说的是**跨到设备/数据库那一侧**的线还没接上，别把两张表读成一张。

### 5.1 `RESOURCE_LEASE_MISSING` 那一条：修法与测试都已在隔离环境里验过

本轮没有直接改仓库（扫描占着工作区），而是用 `git archive HEAD` 在 `/tmp/atest-probe` 建了一份**独立可编译可跑测试**的副本，把修法在那里跑通：

| 步骤 | 结果 |
|---|---|
| 未改代码 + 草稿测试 | `pass 2 / fail 2` —— A 与 C 红，**A0 与反向那条绿**（夹具忠实） |
| 改 `walk` → 三层，且把前置的 `scenario.targets.some(...)` 换成 `deriveTargets(三层).some(...)` | 草稿 `pass 5 / fail 0`，且 `lint.test.ts` 原有 **70 条全绿** |
| 整个 `packages/engine/test/*.test.ts`（改完之后） | **383 全绿**（浏览器那条一开始红是因为临时目录里没软链 `esbuild`，**与改动无关**，补软链后绿） |
| **只改 `walk`、不改 `targets` 那一半** | **只有 B 红**（`pass 4 / fail 1`） |

**最后一行是这一节的重点。** "改两处"里第二处最容易被人当成多余顺手删掉，而它删掉之后 A/C 全绿、扫描全绿、CI 全绿 —— 于是 `setup` 里那个无租约 `tap` 悄悄回到漏报状态，且没有任何测试会响。**B 那条测试唯一的存在理由就是让这次"顺手"变贵**，而它值不值这条测试，不是靠我觉得，是靠"把另一半退回去看谁会红"测出来的。

**两处改动缺一不可的原因**（也解释了为什么 B 与 C 覆盖的不是同一件事）：C 的 `body` 里有 `device`，所以 `scenario.targets` 含 `android`，那个 `.some()` 前置**本来就成立** → C 只受 `walk` 影响；B 的 `body` 里没有任何移动端步骤，`targets` 是 `[]` → B **只受前置条件影响**。两条同名同因的漏报，被两个不同的开关管着。

**上面那张表现在有仓库内的等价物了**（`f690cec`）：`tooling/mutate/lease-scope.json` 把"改回去看谁会红"变成 4 条正式变异，每条**各红一条不同的测试**：

| 变异 | 结果 | 红的是哪条测试 |
|---|---|---|
| S1 三层退回只看 `body` | caught | **A**（setup 里的租约看不见 → 误报） |
| S2 前置退回 `scenario.targets` | caught | **B**（body-only 的 targets → 仍漏） |
| S4 整块"逐步骤规则"改成三层 | **survived（刻意，`expect:'equivalent'`）** | —— 见下 |

**"各红一条不同测试"才是这几条测试不是冗余的证明**，比"全绿"有力得多：全绿只说明没坏，各红一条才说明每条各守一处。

⚠ **这张表本轮重写了一遍**，因为判据本身换了形状（作用域感知之后已经没有 `walk` 那一段可锚，
三条老锚点全部失效，`mutate.specs.test.mjs` 第 23 条把它们全报成"锚点落不到代码上，跑了等于没跑"）。
现在 8 条：S1/S2 还是上面那两条，**新增 S3/S5/S6/S7 守作用域那一半、S8 守嵌套那一半**（见 §3.8），S4 仍是刻意等价。
**变异集跟着判据漂是常态而不是事故** —— 记在这里是因为"spec 文件红了一排"很容易被读成
"我的改动引入了回归"，而它真正说的是"这些锚点指向的代码已经不在了"。
**判据变了而 spec 没跟着改，比 spec 红更糟：那 4 条会安静地永远 caught 不了任何东西。**

**其中 S7 是本轮最贵的一条**：三层改成"一次连续遍历"之后，游标得跨层传递，
而我第一版每层各自从 `false` 起 —— 那等于把 §5.1 whole 节讲的 A 那一格**重新变成误报**，
而当时手上所有测试全绿（新加的四条都是单层场景，碰不到这条路径）。
**写第二版修复时把第一版的修复吃掉了**，这一句本身就是本仓反复记的那族缺陷的标准剧本。

| 把"继承"写成"共用同一个槽对象" | 「两支各自 device」那条 + 嵌套那条 | T9 |

**最后三行是同一轮里第二次修这条缺陷时补的**，而且 T8/S8 这一对值得单独看：
两侧都是"嵌套时少继承一层"，都**只有嵌套形状能抓**，
所以两侧的测试都得是新形状 —— 上一轮那批**顶层 `parallel`** 形状的测试对它们**全绿**。
**"上一轮的测试全绿"从来不等于"这一轮没有缺陷"，它只等于"上一轮那个形状没坏"。**

**"还的 id 集合 == 拿的 id 集合"这个写法要单独说一句**：我第一版断言的是"release 调了几次"，
而那种写法能被"把同一台还两遍、另一台不还"骗过 —— 那在真农场里意味着一台被重复标记已还
（可能已经发给别人了）、另一台永远占着。**计数相同而归属错误，是这一族最典型的假绿形状。**

**L4b 是补出来的，不是我一开始想到的。** 原来的 L4 抓不到 `every → some` 那个变异
（场景里 `else` 分支那个裸 tap **无论如何都会报**，断言恒真、对那个变异**空转**），
是 S6 报 survived 之后回头读测试才发现的。**"这条测试红了"和"这条测试能红"是两件事。**

**S4 是这份变异集里唯一预期不被抓的**，而它记的是**我本来会做的那个越界动作**：把 `walk(scenario.body)` 那一大块整体改成三层，一次"修好"10 条规则。它 survived，**而 survived 在这里不 licensed 到"这么做没问题"** —— 现有测试对"teardown 里的裸 sleep 算不算 flake"没有任何期望，所以它不红只说明没人写过这个期望，不说明改了是对的。判读必须停在"等价/无结论"，**也别顺手补一条测试把它钉住**：先有人把那个产品问题答了，再决定钉哪一边。

**这份修法的落地状态**：测试与变异都已进仓库，`hover-then` / `lint-race`（两份 testFile 指向 `lint.test.ts` 的）也在新代码上重跑过（7/7、12/13+1 等价）。**没做的是把全部变异集在新 `lint.ts` 上重扫一遍** —— 本轮判定过只有那 3 份与 `lint.ts` 有关（按 `cases[].file` 与 `testFile` 两个方向都查过），所以没重扫的那 14 份它们的靶子一字未动。
