## 0. 七个承重问题的答复与造成的改动

**答复**：C1 = **能配合改代码**（利好）；C2 = **全选**（原生+RN / Flutter / H5-WebView 含小程序 / Unity-Cocos-canvas 自绘 —— 最重的答案）；C3 = **iOS + 鸿蒙 NEXT + 压测全在范围内**；C4 = **有成堆 Excel/禅道/Jira 存量**（改变排期）。

| 答复 | 造成的实质改动 | 落在哪 |
|---|---|---|
| **C1 能改代码** ✅ | 定位走阶梯第 1 级；WebView 可开 debug；可装测试 CA 抓 HAR；Android 工作量 ≈1×。Flutter 应**开 semantics + `ValueKey`**，把最重的 pixels 级问题降级为 hierarchy 级 —— 要写进接入验收项强推 | `docs/10` §1 |
| **C2 全选** ⚠ | canvas/自绘使定位阶梯 1–6 级失效，视觉从兜底变主路径；而视觉坐标 `nonReplayable` → **动摇"可回放"这个根基**。解法：**视觉结果编译成图像模板指纹而非缓存坐标**，让视觉定位也确定化 | 新增 `docs/10`；新增 **P2.5，排在 Android 之前** |
| **C3 iOS/鸿蒙/压测** | 三个契约（`TargetAdapter` / `snapshotKind` / `DeviceLease`）**必须 P0 定义**（实现可晚，定义不能晚），否则 IR 与执行层要重写。压测**不能自研** → IR 编译成 k6；并要求 P0 就抽出 `StepExecutor` 接口 + `baseline` 表 | 新增 `docs/09`；`docs/04` P0 补两项 |
| **C4 有存量** ✅ | 迁移是**第一个产生用户价值的里程碑**（P1 首位 M8–M11，因为"把你们现有 3000 条变成可执行资产"比"从零写"推动成本低一个数量级）；**Qdrant 从 P3 提到 P1** —— 用例族聚类去重在迁移场景是必需件而非优化 | 新增 `docs/11`；`docs/04`"P0 不引 Qdrant"对 P1 失效 |

重排后的 P0–P7 见 `docs/09` §5。

### 1.1 未答复期间的推进默认（2026-01 起生效）

用户指示「过程中有疑问先自行决定」，因此以上问题**不再阻塞开工**。这里逐条记下我按哪个假设在推进，以及**哪一条答复会让哪段代码作废** —— 默认不是决定，写下来才可能在答复到达时被推翻，而不是悄悄变成既成事实。

| # | 推进中的默认 | 若答复相反，要回退什么 |
|---|---|---|
| **C5** | 按「约 70% 接口有 spec，且**默认可信度关闭**」实现：spec 只用于生成用例草案，`contract` 策略需显式开启 | 覆盖率低于 ~40% → 「从 HAR/流量反推 spec」从 P1 欠账升级为 P0 前置；`docs/05` A2 的 spec diff 价值大减 |
| **C6** | 按「小规模起步」实现：本地 `launch` 一个 browser，`DeviceLease` 走单进程内存实现 | 大规模 → browser 换成独立 browser service（CDP 池）。契约不变（`DeviceLease` 就是为这个抽象的），变的是实现层 |
| **C8** | **鸿蒙不做任何实现承诺**，`LocatorSpec.by` 里只留 `key`/`predicate` 等枚举位 | 拿不到真机 + DevEco → 从路线图删除，而不是"降级支持"。`docs/09` §3 全部 `[未核实]` 内容不得当作依据 |
| **C9** | 假设**不允许**本地视觉模型 → C 级（pixels）界面按"支持模板指纹、不支持自由视觉问答"实现。**注意**：`maxCostUsdPerResolve` 目前**只是 schema 字段，尚无任何代码读它**（见 §3「定位成本控制」行），所以这条默认下 C 级界面的单次成本暂时**没有闸门**，只有场景级 `maxCostUsd` 兜底 | 允许本地权重 → `docs/10` §3 的成本模型重算，C 级界面从"能做但贵"变"能做且不贵"，P2.5 可提前 |
| **C10** | 按「canvas 约占界面 15%，以按钮/图标类为主」实现模板指纹路线 | 若 canvas 上是**表单流**（输入/选择/滚动列表）→ **这块我仍建议不做**，届时 P2.5 范围重排；若占比 60% → 平台重心整体要重排 |
| **C11** | 假设**没有专职审校人时** → 迁移产物默认 `frozen=false`（进不了 CI），审校队列是第一入口，不做"一键批量冻结" | 有人时 → 加批量审校 + 抽样复核。**反过来（默认冻结 + 事后审）绝不行**：把没断言的用例塞进 CI，红灯会被读成"平台不行" |
| **C12** | 先做**通用 Excel/CSV 导入器**，绕过系统对接 | 具体系统确定后逐个做 API 同步器；导入器的 `CaseDraft` 中间层不变（那才是契约） |

**共同点**：这七条默认全部落在「实现层的量」而不是「契约的形状」。契约（IR / 三契约 / lint 规则）按已确认的决策实现，未决问题只影响先做哪一块、做多大规模 —— 这个分界是刻意的，避免未答复的问题反过来污染数据模型。

| **「schema 有字段、执行侧没人读」这个缺陷类别** | 已出现三次：`maxCostUsdPerResolve`（至今仍未读，见上一行）、`wait.onTimeout:'error'`（解释器只分 continue/其余，那个取值永远走不到）、`assertPerf.maxRegressionRatio`（缺基线时静默不判、照样 pass）、`Match.unordered`（无自洽含义，写了就随机误判）。后三条已在 M0.6 修掉（明细见 `04` §M0.6）。**扫描办法**：列出 ir/src 所有 zod 字段名，逐个查执行侧有没有读过 —— 一次脚本就能跑出来，别靠偶然发现。**残余未读字段是有意分层的**：`targets.ts`/`trace.ts`/`scenario.ts` 的持久化与画像字段属 P1（store 层）与 P2（编辑器），`locator.ts` 的定位字段属 P2.5 —— 它们的"未读"是没开工，不是接错线 | 每次给 IR 加字段时顺手问一句"谁读它"。加字段而没有对应测试 = 埋一颗"配置写了但没生效、还显示成功"的雷，这类雷的共同症状是**用户以为自己在用一个功能，其实没有** |
| **断言自动拆一层 `body`** | `assertions.ts` 里 `const body = value?.body ?? value` —— 断言对象是响应时自动拆一层 `body`，让 `$.id` 直接命中响应体的 id（90% 的断言因此更短）。代价：**响应体自己就有 `body` 字段时无法区分**"我要响应的 body 字段"和"整个响应体" | 已知取舍，有测试固定行为（`browser.test.ts` 里那条注释）。要消歧就得引入 `$..body` 与 `$.body` 的显式区分，或者规定 jsonPath 一律从响应体起算 —— 后者更干净，但会让所有既有写法整体位移一层，宜早不宜迟 |
| **多平台设备统一调度** | 安卓/iOS/鸿蒙共用一套租约与 agent 形态的可行性验证；Mac 池与 Linux 池混排的调度约束（`docs/09` §1.3） | 未写；契约已定，调度器未设计 |
