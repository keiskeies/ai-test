# 10 · 视觉类界面（canvas / Unity / Cocos / Flutter 空树）的定位与可回放化

**为什么单独一份**：范围确认里最重的答案是"包含 Unity/Cocos/canvas 自绘"。它使 `docs/02` §6 定位阶梯的 **1–6 级全部失效**（没有 testid、没有语义、没有可锚定的兄弟节点），只剩 Set-of-Mark 视觉和纯坐标两条 AI 路径。而视觉坐标是 `nonReplayable` 的 —— 分辨率/DPR/视口/窗口缩放一变就废，这**直接动摇"可回放、可信证据"这个平台根基**。

**本文的解法一句话**：**把视觉定位的结果编译成图像模板指纹，而不是缓存坐标** —— 让视觉定位也变成确定性的、可 diff 的、可人审的产物。等价于 `docs/00` §5.1「LLM 是一次性定位器编译器」在像素世界的推广。

排期 **P2.5，排在 Android 之前**（`docs/09` §5）：这是纯软件问题，先在可控范围内解掉，再去碰设备运维。

---

## 1. 界面形态分级（先分类，再决定每类花多少）

| 级 | 形态 | 快照 | 定位可用手段 | 可回放性 | 平台该给的承诺 |
|---|---|---|---|---|---|
| **A** | 标准 DOM / WebView / 原生 / RN / 鸿蒙 ArkUI | `aria`/`hierarchy` | 阶梯 1–7 | **强** | 全功能，可进 CI |
| **B** | Flutter **开了 semantics**（能改代码 → 强推这条） | `hierarchy` | 阶梯 1–6（`ValueKey` = testid） | **强** | 全功能 |
| **B'** | Flutter 未开 semantics | 实际 `pixels` | 阶梯 7–8 + 模板 | 中 | 只承诺 AOT 断言 + 回归，不承诺精细交互 |
| **C** | Unity/Cocos/自绘 canvas/游戏 | `pixels` | 模板匹配 + 视觉 grounding | **中，靠模板质量** | 承诺"关键界面回归"，**不承诺复杂表单流** |
| **D** | 视频流/摄像头/动态像素（画面本身在变） | 无稳定模板 | 只能语义判定 + 人工 | **无** | **明确不支持**，写进文档 |

**B→B' 是投入产出比最高的一件事**：被测端能配合改代码（已确认），Flutter 侧开 semantics + 给关键控件加 `ValueKey`，就把整个 C 级问题降级成 A 级。**这条要写进接入文档、并作为接入验收项推给客户** —— 它比测试侧任何投入都便宜。同理 Unity 侧：很多自绘 UI 其实是"UGUI/FairyGUI + 少量真 canvas"，**先把 B 级部分识别出来剥离掉，剩下的 C 级往往只有 10–20% 的界面**。不要一上来按"全是 canvas"设计整个方案。

## 2. 核心机制：模板指纹（`templateFingerprint`）

`LocatorSpec` 新增一种落点（第 9 级，`pixels` 世界的第 1 级）：

```jsonc
"locator": {
  "intent": "右上角的金币图标",
  "compiledTo": {
    "kind": "template",
    "imageRef": "art://tpl/sha256:...",      // 内容寻址存储的模板图（PNG）
    "confidence": 0.82,                       // 首次匹配得分
    "searchHint": { "roi": [0.78,0.02,0.12,0.06], "scaleRange": [0.9,1.1] },
    "nearText": "钻石 128",                   // 可选：视觉 OCR 锚点，抗同图多实例
    "occurrences": 1,                         // ★ 全帧唯一性检查（=0 或 >1 是致命信号）
    "recordedAt": "…", "minScaleInvariant": true
  },
  "fallbacks": [ { "kind": "visionGround" } ]  // 模板不中才调模型
}
```

**编译过程（设计期，一次性）**：
```
视觉模型 grounding 得到 bbox
  → 裁剪 bbox 周边带上下文的区域（不是紧贴边框：留 2–6px 边，避免边界抖动导致匹配失败）
  → 记录 ROI（bbox 外扩 30–50%）而不是全帧搜索   ← 决定性能与误匹配率
  → 全帧跑一次匹配，统计 occurrences（>1 则该模板不合格，必须加 nearText 或换区域）
  → 存模板图 + 参数 + 首次得分 → 人审一眼截图上圈出来的位置
```

**匹配执行（运行期，零 LLM）**：
| 项 | 做法 | 为什么 |
|---|---|---|
| 算法 | 多尺度归一化互相关（NCC）或旋转不变匹配（Airtest 用类似 `aircv` 的思路 `[未核实]`）；OpenCV.js/WASM 或 native `opencv4nodejs` | 纯 CPU，零成本，**确定性** |
| ROI 限定 | 只在 hint ROI 内搜，命中即止 | 全帧多尺度搜索在 1080p 上是 10²ms 量级，会吃掉整个步骤预算 |
| 多尺度 | `scaleRange` 由设备 DPR 推得，不放开全尺度 | 尺度放开的代价是误匹配与耗时同时上升 |
| 同图多实例 | `occurrences > 1` 时**必须**用 `nearText`（OCR 邻近文本）或序号消歧，否则直接失败 | 静默选错第一个实例是 pixels 世界的头号事故 |
| 点击点 | 匹配框中心 + `hitTarget` 检查，**绝不用模型给的原始像素**（`docs/00` §8 视觉定位错位） | — |
| 失败 | 降级到视觉 grounding → **成功则自动提"模板更新 diff"**（旧模板图 vs 新模板图 + 前后截图）进审校队列 | 与 A 级自愈同一套治理：自愈=软失败+人审（`docs/00` §5.6） |

**模板老化是被低估的运维问题**（比 A 级的定位器老化更频繁）：皮肤/主题/图标重绘/活动 banner/DPR 变化都会让模板失效。对策：
- `locator_stats` 增加模板维度的 `heals`（同一套排名机制，`docs/00` §5.11 → "这个模板本周失效 27 次，点开重录"）。
- **支持按界面批量重录**（一次截图 → 批量重跑所有该界面模板的匹配 → 列出全部失效项 → 一键在新截图上重新框选）。这是 pixels 世界的"批量修定位器"，没有它，C 级界面的维护成本会让人放弃平台。
- 皮肤类 app 需要**按主题各存一套模板**（环境/配置维度），否则换个皮肤全红。

## 3. 视觉 grounding：作为编译器，不作为运行时

模型输入的构造（pixels 世界的"上下文构建"，成本敏感度极高）：

| 要点 | 做法 |
|---|---|
| 降采样 | **≤1024px / JPEG q70**（`docs/00` §6.9：近零精度损失换 3–5× token 削减） |
| 坐标回映射 | 模型输出归一化坐标 → 原图分辨率 → 设备坐标（DPR/裁剪偏移全链路记录） |
| SoM 优先于自由坐标 | 编号框覆盖候选元素，模型答"点 7" → 有语义把手可缓存；自由坐标什么都没留下 |
| 候选融合 | 用轻量 grounding 模型（Aguvis-1.5B / UI-TARS-7B 本地权重）**与 OpenCV 候选检测**（边缘/连通域/图标性启发）取交集，要求一致才采纳（`docs/00` §5.10 两定位器取交集模式） |
| 小目标 | coarse-to-fine 裁剪放大（Aguvis 思路）；**高分屏 desktop 是已知塌陷区，不承诺** |
| 输出契约 | 强制 `generateObject`：`{found, candidateId, bbox, confidence, why}` —— 不接受自由文本里捞坐标 |

**本地权重是经济前提**：pixels 世界如果每次兜底都调云端视觉模型，成本会随 C 级界面数线性爆炸（`docs/00` §6.9 的 $1–4k/晚就是这么来的）。`visionGround` 分组的 `localFirst: true`（`docs/03` §1）在这里是**必需而非可选**。若客户环境不允许本地模型（`docs/03` §5 的 `allowExternalLlm` 反向情形也有：数据不能出内网但内网没有视觉模型），**要明确告知 C 级界面无法支持**，而不是硬接。

## 4. 视觉类断言：把不可靠的那一半隔离掉

`pixels` 世界的断言能力天生弱，必须分级承诺（`docs/09` §1.2 的 `snapshotKind` 落地）：

| 断言 | 手段 | 可靠性 | 门禁 |
|---|---|---|---|
| 界面元素存在 | 模板命中 + 置信度阈值 | **高**（确定性） | ✅ |
| 界面元素消失 | **上一帧模板命中 + 本帧未命中**（成对判据） | 中-高 | ✅ |
| 数值/文案变化 | **区域 OCR**（tesseract.js/PaddleOCR `[未核实]`）→ 结构化值 → 复用普通 matcher | 中（OCR 有错字，需置信度与字符集约束） | ✅ 但断言写成"数值区间/正则"而非字面 |
| 画面变化量 | 区域像素 diff（SSIM/感知哈希）+ 阈值 + 忽略区 | 中 | ⚠ report-only 起步，人审基线后才可门禁 |
| **"画面是否显示正确"** | `assertLlm` + 强制证据引用 | **低** | ❌ **永不门禁**（`docs/02` §4） |
| **否定断言（"弹窗没出现"）** | ⚠ 禁用视觉模型 | **极低**（视觉模型过度报告存在） | ❌ 只能走"模板未命中"路径 |
| 动画/过渡正确性 | 帧序列模板命中时序 | 低 | ❌ 不支持，明确写出 |

**必须有的一条元规则**：C 级界面的报告要**在场景级别标注"视觉类断言占比"**。一个 80% 依赖 `assertLlm` 的场景，其红绿含义与 A 级场景完全不同 —— 这个信息不显示出来，就是在骗用户，而且会被第一个月就发现。

## 5. 与 A 级世界的统一：IR 层怎么表达

对 IR 而言 pixels 只是 `snapshotKind` 不同，**节点类型不换**（避免"两套用例语言"）：

```jsonc
// 同一个 tap 节点，两处 locator 编译产物不同，其余完全一致
{ "kind": "tap", "target": { "intent": "金币图标" } }
// A 级编译 → { primary:{by:"testid",...}, fingerprint:{ariaSubtreeSha:...} }
// C 级编译 → { compiledTo:{kind:"template", imageRef:"art://tpl/..."} }
```

静态闸新增（`docs/02` §7 的扩展）：

| 规则码 | 检查 | 级别 |
|---|---|---|
| `PIXEL_ASSERT_ON_NONHIERARCHY` | 对 `pixels` 目标写 `uiPredicate{state:visible}` 等层级谓词 | **error**（类型错误，不是运行时失败） |
| `NEGATIVE_ASSERT_VISION_BASED` | 否定断言依赖视觉模型判定 | **error** |
| `TEMPLATE_NOT_UNIQUE` | 模板 `occurrences > 1` 且无 `nearText`/序号 | **error** |
| `TEMPLATE_NO_ROI` | 模板无 ROI（全帧搜索） | warning（性能） |
| `LLM_ASSERT_RATIO_HIGH` | 场景内 `assertLlm` 占比 > 50% | warning（红绿可信度） |
| `VISION_STEP_IN_CI_GATE` | `nonReplayable` 步骤出现在 `frozen=true` 场景里 | **error** |

最后一条是**可回放性承诺的技术守卫**：视觉自由坐标永不进 CI 门禁。有了它，"我们支持 canvas" 和"我们的结果可信"两件事不打架。

## 6. 需要用户拍板的问题

| # | 问题 | 为什么影响大 | 我的默认 |
|---|---|---|---|
| V1 | **Flutter 侧能否开 semantics + 加 `ValueKey`？** | 能 → B' 降级为 B，C 级问题可能直接消失大半（`docs/09` 已确认"能改代码"，但 Flutter 这项要具体确认，因为它需要改业务代码而不只是加属性） | 按能改推，作为接入验收项 |
| V2 | Unity/Cocos 部分**具体是什么界面**？（游戏主玩法？活动页？登录？自绘列表/输入框？） | 表单流（输入/选择/滚动列表）在 pixels 世界几乎不可做；若核心流程是表单，**我会建议这块不做而不是硬做** | 只承诺按钮/图标/静态界面回归 |
| V3 | C 级界面**大约占测试面的百分之多少**？ | 10% → 按本文兜底做；60% → 平台重心要变（视觉测试平台），定位/成本/维护模型整体重排 | 假设 15% |
| V4 | 界面**有无多皮肤/主题/活动换肤**？ | 有 → 模板要按主题各存一套（§2），维护成本 ×皮肤数；这是能否长期运营 C 级的关键 | 支持按环境/配置分套模板 |
| V5 | 设备/窗口**分辨率是否固定**？ | 固定 → 模板极稳；多分辨率 → 必须多尺度匹配（成本与误匹配率都上升） | 移动端固定、Web 允许 2 档 |
| V6 | 是否允许**本地视觉模型**（GPU 机器 + UI-TARS/Aguvis 权重）？ | 不允许且内网无视觉模型 → **C 级明确不支持**（§3 的经济前提） | 允许，本地优先 |
| V7 | OCR 是否有**中文场景**（字体小、艺术字、描边）？ | 中文艺术字 OCR 错误率高，直接影响 §4 的数值断言可行性 | 数值类断言只用 OCR 且标置信度 |
| V8 | 小程序具体是**微信还是其他**？登录怎么解决？ | 小程序在微信内运行，登录依赖微信账号+扫码/风控，自动化难度与原生完全不同（`docs/07` A-6 仍未答） | **仍按未定处理**，不排期 |
